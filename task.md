# Найденные странности и несоответствия: web-интерфейс ↔ backend

Собрано при сверке `server/data/index.html` с `server/src/webhandler.cpp`,
`server/src/schedule.cpp`, `server/src/mp3handler.cpp`. Отсортировано по
критичности для реального использования (курс Випассаны, гонг не должен
"молчать" по недосмотру).

## 🔴 Критично

### 1. Навигация по дням в UI на самом деле их АКТИВИРУЕТ, а не просматривает
`schedNavDay()` (index.html:753) при клике на стрелки `«`/`»` вызывает
`schedActivateSilent(day)` → `POST /api/day/activate?n=N`. Это не просмотр —
это переключение живого расписания на сервере (`sched_activateDay`,
schedule.cpp:239). При этом:
- Backend уже готов к безопасному просмотру: есть `GET /api/day?n=N`
  (`handleDayGet` → `sched_dayJSON`, **не мутирует** состояние), но фронтенд
  этот метод нигде не вызывает.
- В отличие от удаления записи (`deleteSched` спрашивает `confirm()`),
  переключение дня стрелками не спрашивает вообще ничего.
- Итог: оператор, просто листающий дни "посмотреть, что там на 5-й день",
  реально переключает боевое расписание на день 5. Если это происходит
  случайно вечером — весь следующий день гонг звонит не по той программе.

**Как должно быть:** стрелки должны звать `GET /api/day?n=N` для превью,
а отдельная явная кнопка "Activate this day" (с подтверждением) — POST
`/api/day/activate`.

### 2. Автопереключение дня не включается само по себе
`sched_check()` пропускает полуночную логику целиком, если
`sched_getActiveDay() == -1` (schedule.cpp:66-67). А `/activeday.conf` не
поставляется в образе прошивки (в `server/data/` его нет). Значит на свежем
устройстве (или после сброса SPIFFS) многодневный курс **не стартует сам**:
сервер вечно крутит `/gong.conf` как есть (по факту — это копия день00/11,
"лёгкого" расписания заезда/отъезда, а не полной программы курса из
day01–day10), пока кто-то не зайдёт в UI и не кликнет по дню хотя бы раз.
Ни в UI, ни в логах это состояние никак не подсвечено — `schedDayLabel`
покажет "День 00" в обоих случаях: и когда день реально активирован, и когда
`activeDayNum == -1` (index.html:743-745, `schedDayView = 0` по умолчанию).

### 3. Нет отката к day00 после day11 и нет об этом сигнала
См. `process.md` §5. После последнего дня курса сервер тихо продолжает
играть по day11 бесконечно. UI не показывает "курс завершён, расписание
не меняется" — `renderSchedDayHeader()` просто напишет "День 11" и на этом
всё. Для персонала это будет выглядеть как рабочая система, хотя по факту
никто не переключил её на новый заезд.

### 4. Пропуск полуночи = день не переключится вообще
Если устройство было выключено/перезагружалось именно в минуту 00:00 (или
время стало валидным только после 00:00 — например RTC синхронизировался в
08:00), день не advance'ится, потому что логика реагирует на живой тик
`h==0 && m==0`, а не на "дата отличается от сохранённой". Ни один эндпоинт
в API не даёт это увидеть или поправить руками, кроме всё той же
мутирующей навигации стрелками (см. п.1).

## 🟡 Существенно

### 5. Треки 3–99 разрешены в UI, но upload-эндпоинта нет
Модалка добавления/редактирования записи (index.html:337) принимает
`track` от 1 до 99, backend тоже это принимает (`sched_add`/`sched_edit`,
schedule.cpp:103,114 — диапазон 1–99). Но `SPIFFS/data` содержит только
`0001.mp3` и `0002.mp3`, и в `webhandler.cpp` нет ни одного маршрута для
загрузки файлов (`grep upload/multipart` — пусто). Если оператор укажет
`track=5`, `mp3handler.cpp:26-30` тихо залогирует `[MP3] File not found` и
ничего не воспроизведёт — молча, без сообщения в веб-интерфейсе.

**Как должно быть:** либо ограничить `track` в UI реальным списком файлов на
SPIFFS (нужен эндпоинт вроде `GET /api/tracks`), либо добавить upload.

### 6. Несколько записей на одно и то же время — сработает только первая
Ни backend (`sched_add`/`sched_edit`), ни UI (модалка) не проверяют
уникальность `hour:min` среди записей одного дня. `sched_check()` при этом
использует `break` после первого совпадения (schedule.cpp:95) — вторая
запись на то же время в этом же дне никогда не сработает, но в таблице
расписания в UI обе будут показаны как обычные "ON"-записи, без какого-либо
предупреждения о конфликте.

### 7. `/api/days` отдаёт `count: 12`, захардкожено отдельно от диапазона проверки
`handleDaysStatus()` (webhandler.cpp:259) пишет `doc["count"] = 12;` как
отдельную константу, а проверки диапазона в `handleDayGet`/`handleDayActivate`
используют `n < 0 || n > 11` как отдельный литерал. Сейчас они согласованы
(0–11 = 12 значений), но это два независимых места, которые ничто не
связывает — измени одно и забудь про другое, и `/api/days` начнёт врать
фронтенду о реальных границах. Фронтенд использует свой третий захардкоженный
литерал (`Math.max(0, Math.min(11, ...))`, index.html:754) вместо того чтобы
взять границу из ответа `/api/days`.

### 8. Комментарии в коде ссылаются на несуществующий NTP/Wi-Fi-STA путь
`schedule.cpp:30` — "Uses system time configured via configTime() in
wifi_connect()" и `:44` — "WiFi being connected does NOT mean NTP has synced
yet". Ветка `only_wifi` убрала клиентский Wi-Fi (`wifi_connect()` больше нет
нигде в дереве — сервер работает только как автономная точка доступа,
`wifi_startAP()`, без интернета и без `configTime()`). Время теперь
приходит **только** из DS3231 или ручного ввода. Комментарии вводят в
заблуждение о том, что теоретически возможна NTP-синхронизация — по факту
это мёртвый путь, оставшийся от предыдущей архитектуры.

## 🟢 Мелкое / документация

### 9. `server/IMPORTANT` — целиком про LoRa (SX1278, пины GPIO5/14/18/19/23,
частоту 433 МГц), которого в этой ветке уже нет ни в коде, ни в железе
согласно `only_wifi`. Файл лежит в корне `server/` и выглядит как актуальная
памятка по пинам, хотя пины LoRa там больше не задействуются.

### 10. Клок на фронтенде (`espTime`/`espTimestamp`, index.html:383-401)
экстраполирует время локально между опросами `/api/status` (раз в 5 c) —
если вкладка браузера была свёрнута/фоновая и не тикала, при возврате
кажущееся время может разойтись с реальным до следующего `refreshAll()`.
Не влияет на реальное срабатывание гонга (это делает сервер по своим часам),
но может вводить в заблуждение персонал, смотрящий на countdown.

### 11. `computeNextGong()` (index.html:414) считает обратный отсчёт только
по записям **активного** дня. Прямо перед полуночью, если сегодня последний
гонг уже прозвенел, таймер покажет обратный отсчёт до **того же** времени
завтра по **текущему** (ещё не переключившемуся) дню — на секунду-две после
полуночи, когда день уже переключился на сервере, это разойдётся с реальным
расписанием, пока не отработает следующий `loadSchedules()` (раз в 5 c).
Косметика, но стоит знать.

## Итог
Базовый цикл "добавить/изменить/удалить запись → сработать в нужную минуту"
у web-интерфейса и backend'а согласован полностью (валидация времени/трека/
loop идентична по обе стороны). Все найденные проблемы — вокруг **многодневной
модели курса**: она не документирована как отдельная фича ни в UI, ни в
комментариях кода, включается только неявным побочным эффектом клика по
стрелке навигации, не имеет защиты от случайной активации, не переживает
пропуск полуночи и не имеет явного финала/сброса после последнего дня.
