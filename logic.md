# Логика системы Gong LoRa

Этот файл описывает **логику работы кода** (что происходит и почему), а не архитектуру
и не инструкции по прошивке — они в `README.md`. Здесь — по модулям, с указанием
файлов и последовательности выполнения.

Система состоит из двух независимых прошивок:

- **`server/`** — ESP32 с WiFi, веб-интерфейсом, расписанием и LoRa-передатчиком.
- **`client/`** — ESP32 только с LoRa-приёмником и MP3-плеером, без WiFi и без своего расписания.

Оба используют RadioLib (SX1278) и ESP32-audioI2S (MAX98357A), и оба разбивают работу
на два ядра ESP32: **Core 0** занят радио (прерывание DIO0 + FreeRTOS-задача),
**Core 1** — `loop()` из Arduino framework (веб-сервер / MP3-декодер / диспетчеризация команд).
Это разделение существует потому, что MP3-декодированию и I2S-DMA нужно "кормление"
почти на каждой итерации `loop()`, а радио должно реагировать на прерывание DIO0
без задержек — если оба сделать в одном `loop()`, аудио или приём LoRa будут прерываться.

## 1. Сервер (`server/src/`)

### 1.1 `main.cpp` — точка входа

`setup()` выполняет модули строго в таком порядке:

1. `SPIFFS.begin(true)` — если файловая система не смонтировалась, сервер зависает
   в `while(true) delay(1000)` (без файловой системы работать бессмысленно: там и
   MP3, и расписание, и конфиги).
2. `onScheduleTrigger = onGongFire` — регистрирует колбэк, который `schedule.cpp`
   вызовет, когда наступит время по расписанию.
3. `rtc_setup()` — пробует прочитать время с DS3231 *до* WiFi, чтобы расписание
   могло работать даже если WiFi ещё не поднялся или недоступен.
4. `mp3_setup()`, `lora_setup()`, `sched_setup()`.
5. `web_setup()` — последним, т.к. подключение к WiFi может занять до
   `WIFI_TIMEOUT_MS` (10 сек), и это не должно блокировать инициализацию LoRa/аудио.

`loop()` на Core 1 каждую итерацию:
- обслуживает HTTP-запросы (`web_loop()`);
- **8 раз** вызывает `mp3_loop()` за один проход — ESP32-audioI2S нужно "кормить"
  часто, иначе в потоке появляются щелчки/обрывы;
- раз в секунду вызывает `sched_check()` (проверка расписания не должна быть
  чаще — минутная точность делает более частые проверки бессмысленными);
- раз в `HEARTBEAT_INTERVAL_MS` (30 сек) шлёт HEARTBEAT всем LoRa-клиентам.

`onGongFire(track, loop)` — единая точка, откуда стартует звонок по расписанию:
**сначала** уходит LoRa-команда (`lora_sendGong`, блокирует Core 1 до завершения
TX, ~170 мс), **потом** запускается локальное воспроизведение. Порядок важен —
так сервер и клиенты начинают играть звук в одно и то же время, а не сервер
на ~170 мс раньше.

### 1.2 `lorahandler.cpp` — LoRa-передатчик/приёмник сервера

Это самый сложный модуль сервера. Ключевая идея: **вся работа с радио происходит
в отдельной FreeRTOS-задаче `loraTask` на Core 0**, а Core 1 только кладёт запросы
в очередь и (для GONG) ждёт семафор.

**Очереди/примитивы синхронизации:**
- `txQueue` (глубина 2) — запросы на передачу от Core 1 к Core 0.
- `txGongDone` (бинарный семафор) — Core 0 отдаёт его, когда TX пакета GONG
  завершился; `lora_sendGong()` блокируется на нём, чтобы вызывающий код
  (главный `loop()`) знал точный момент, когда эфир свободен и можно стартовать
  локальный плеер.
- `clientsMtx` — защищает массив `clients[]` от гонки между Core 0 (пишет при
  приёме ACK) и Core 1 (читает через `lora_clientsJSON()`/`lora_clientCount()`
  по HTTP-запросам).
- `dioFlag` (volatile bool) — выставляется в прерывании `onDio0()` по фронту
  DIO0 (событие срабатывает и на TX-done, и на RX-done — SX1278 конфигурируется
  так, что оба используют один и тот же пин).

**Состояние `loraTask` — простой стейт-машина без блокирующих ожиданий:**
1. Если идёт передача (`txBusy`) — ждать `dioFlag`, при появлении завершить TX
   (`finishTransmit`), для GONG отдать `txGongDone`, вернуться в приём
   (`startReceive`).
2. Иначе, если в `txQueue` есть запрос — начать `startTransmit`, выставить `txBusy`.
3. Иначе, если `dioFlag` установлен — значит, принят пакет: прочитать, разобрать.

Приоритет "TX важнее RX" неявный: TX стартует, как только освобождается место
в очереди, до проверки RX-флага — поэтому если сервер одновременно шлёт GONG и
получает ACK, ACK будет обработан только после завершения текущей передачи.

**Формат сообщения**: `[1 байт тип][JSON payload]`. Перед отправкой GONG/HEARTBEAT/STOP
подписываются HMAC-SHA256 (усечённым до 8 байт/16 hex-символов) — `computeHMAC()`
считает подпись по связке `msgType + payload` с общим секретным ключом
`LORA_HMAC_KEY` (должен совпадать на сервере и во всех клиентах). Подпись
дописывается прямо в JSON как поле `"sig"` перед отправкой (см. `loraSend()`).
SCHEDULE **не подписывается** — расписание пока не проверяется клиентом
(`MSG_SCHEDULE` на клиенте только логируется, не применяется — см. §2.2).

**Приём ACK и учёт клиентов** (`upsertClient`):
- Если клиент уже известен — обновляет RSSI, `lastSeenMs` и экспоненциально
  сглаживает RTT (вес 70% старому значению, 30% новому: `(old*7 + new*3)/10`).
  Из RTT вычитается средняя случайная задержка ACK клиента
  (`ACK_RANDOM_DELAY_AVG_MS = 45` — клиент специально ждёт 10–80 мс перед
  отправкой ACK, чтобы избежать коллизий в эфире при broadcast нескольким
  клиентам одновременно; сервер компенсирует эту задержку при расчёте RTT).
  One-way задержка = `rttMs / 2`.
- Если клиент новый и есть место (`< MAX_CLIENTS = 16`) — добавляется.
- Если места нет — ищется самый "старый" (давно не отвечавший) клиент; если он
  не отвечал дольше `CLIENT_TIMEOUT_MS` (90 сек), он вытесняется новым.
  Иначе новый клиент просто игнорируется (лог "MAX_CLIENTS reached").

`lora_clientsJSON()`/`lora_clientCount()`/`lora_getAvgOneWayMs()` фильтруют
клиентов по `age <= CLIENT_TIMEOUT_MS` "на лету" при каждом обращении — то есть
устаревшие клиенты не удаляются из массива активно, а просто перестают
попадать в отчёты, пока их не вытеснит новый (ленивая инвалидация).

`lora_sendHeartbeat()` **пропускает отправку**, если в `txQueue` уже что-то
ждёт (`uxQueueMessagesWaiting > 0`) — HEARTBEAT низкоприоритетен и не должен
конкурировать с GONG/STOP за то же место в очереди глубиной 2.

### 1.3 `mp3handler.cpp` — локальное воспроизведение (сервер)

Обёртка над библиотекой ESP32-audioI2S:
- Внешняя громкость 0–30 транслируется во внутреннюю шкалу библиотеки 0–21
  (`applyVolume()`).
- `_startPlay(track)` открывает `/%04d.mp3` (например, `/0001.mp3`) из SPIFFS.
  Громкость сначала выставляется в 0, а через 40 мс (`mp3_loop`, ветка
  `ramping`) поднимается до целевой — это гасит щелчок в динамике при старте
  потока на полной громкости.
- Зацикливание (`loop` параметр 1–7) реализовано не средствами библиотеки, а
  вручную: `loopRemain` хранит число оставшихся повторов; `mp3_loop()` следит
  за `audio.isRunning()`, и если поток "молчит" **20 итераций подряд**
  (не сразу — чтобы не спутать паузу между DMA-чанками с реальным концом
  трека), считает трек законченным и либо перезапускает его
  (`loopRemain > 0`), либо приглушает громкость.

### 1.4 `rtchandler.cpp` — DS3231

- `rtc_setup()`: пробует найти DS3231 на шине I2C (стандартные пины ESP32
  SDA=21/SCL=22). Если чип не отвечает — сервер продолжает работать без RTC
  (`rtcPresent = false`), полагаясь только на NTP/ручное время.
- Если чип найден, но `rtc.lostPower()` (батарейка CR2032 разрядилась или это
  первое включение) — время из чипа заведомо мусорное, оно **не** загружается
  в систему.
- Иначе время из DS3231 сразу пишется в системные часы ESP32
  (`settimeofday`) — это даёт корректное время расписанию даже до того, как
  WiFi/NTP успеют подключиться (может занять минуты или не сработать вовсе,
  если нет интернета).
- `rtc_syncFromSystem()` вызывается после успешной синхронизации по NTP
  (`webhandler.cpp: wifi_connect()`) и после ручной установки времени
  (`webhandler.cpp: handleTimeSet()`) — таким образом DS3231 всегда содержит
  "последнее известное хорошее" время и переживёт следующий сбой питания без
  доступа к интернету.

Итоговый приоритет источников времени: **NTP (если WiFi подключен и не
отключён вручную) > RTC (если присутствует и не потерял питание) > ручной ввод
> ничего** — эта логика размазана между `rtc_setup()`, `wifi_connect()` и
`webhandler.cpp: handleStatus()` (там же формируется поле `time_source` для UI).

### 1.5 `schedule.cpp` — расписание и многодневные профили

**Хранение**: `entries[MAX_SCHEDULES=32]` в памяти — активное расписание.
Каждое изменение (`sched_add/edit/del`) сразу вызывает `sched_save()`, которое
пишет JSON в `/gong.conf` **и**, если есть активный день
(`sched_getActiveDay() >= 0`), зеркалирует то же самое в `/dayNN.conf` — так
редактирование расписания "на лету" не теряется при следующем переключении дня.

**`sched_check()`** — вызывается раз в секунду из `main.cpp`:
1. Если `getLocalTime()` не вернул время — выход (с логом раз в минуту, чтобы
   не спамить Serial).
2. Время считается валидным, если WiFi подключен (значит, скорее всего, был
   NTP) **или** год в системных часах >= 2024 (значит, время было выставлено
   вручную или из RTC — заводское время ESP32 всегда 1970).
3. В полночь (00:00, с защитой от повторного срабатывания в течение 65 сек)
   пытается автоматически переключиться на файл следующего дня
   (`/dayNN.conf`), если он существует — так недельный/многодневный цикл
   расписаний крутится сам, без участия пользователя.
4. **Anti-double-trigger**: `lastFiredKey` (час*60+минута) и `lastFiredMillis`
   не дают сработать повторно в течение той же минуты — окно 65 сек (не 60)
   специально даёт запас на дрейф NTP-времени в секундах.
5. Перебирает `entries[]`, у первой подходящей enabled-записи с текущими
   `hour`/`minute` вызывает `onScheduleTrigger(track, loop)` — **только одна**
   запись может сработать за минуту (`break` после первого совпадения), даже
   если случайно совпало несколько записей на одно и то же время.

**Многодневные профили** (`sched_dayJSON`, `sched_activateDay`,
`sched_getActiveDay`): до 12 файлов `/day00.conf`...`/day11.conf` на SPIFFS.
`sched_activateDay(day)`:
1. Если файл для `day` ещё не существует — создаётся. **Важный нюанс**: если
   это вообще первая активация дня в жизни устройства
   (`sched_getActiveDay() < 0`, т.е. `/activeday.conf` ещё не создан) — новый
   файл дня "затравливается" текущим расписанием (`sched_toJSON()`), чтобы уже
   введённые пользователем записи не потерялись при первом переходе на
   многодневный режим. Любой следующий новый день создаётся пустым.
2. Текущее расписание сохраняется в файл **старого** дня (`sched_save()` — тут
   `activeday.conf` ещё указывает на старый день, это специально, иначе
   `sched_save()` перезаписал бы файл нового дня старыми данными).
3. Новый день загружается в память (`sched_parseFromPath`).
4. Загруженное записывается напрямую в `/gong.conf` **в обход** `sched_save()`
   (чтобы не задеть файл дня — см. комментарий в коде) — и только теперь
   `/activeday.conf` обновляется на номер нового дня.

Порядок шагов 2→3→4 важен именно из-за побочного эффекта `sched_save()`,
который всегда пишет и в `/gong.conf`, и (если день активен) в файл текущего
активного дня — поменяй порядок, и обновление затрёт не тот файл.

### 1.6 `webhandler.cpp` — WiFi + HTTP REST API

**WiFi**: `web_setup()` сначала пробует `wifi_connect()` (читает
`/wifi.conf`, коннектится как STA, таймаут `WIFI_TIMEOUT_MS`). При неудаче —
`wifi_startAP()` — сервер сам становится точкой доступа с фиксированными
SSID/паролем из `config.h`, чтобы к нему гарантированно можно было
подключиться и ввести данные домашней сети через `/api/wifi/save`.
После успешного STA-подключения — mDNS (`gong.local`), NTP-синхронизация,
`rtc_syncFromSystem()`.

**Авторизация** (`checkAuth`): опциональный Basic Auth (логин фиксирован
`admin`), включается/выключается через `/api/auth/*`. Если выключена или
пароль не задан — пропускает всех. Каждый защищённый обработчик начинается с
`if (!checkAuth()) return;`.

**Маршруты** сгруппированы по назначению — расписание (CRUD), ручное
воспроизведение (`/api/play*`), время, WiFi, авторизация, многодневные
профили. Отдельно для каждого API-пути с телом запроса зарегистрирован
`HTTP_OPTIONS` → `handleOptions()` — это CORS preflight, нужен, чтобы фронтенд
мог ходить на сервер с другого origin (например, при разработке UI отдельно
от прошивки).

`/api/play`, `/api/play/lora`, `/api/play/all` — три разных сценария ручного
запуска гонга: только локально, только по LoRa всем клиентам, или оба сразу
(с тем же порядком "LoRa → потом локально", что и в `onGongFire`, для
синхронности).

`/api/status` формирует сводку и **на лету** решает `time_source` (`ntp` /
`rtc` / `manual` / `none`) — см. §1.4 про приоритет источников времени.

## 2. Клиент (`client/src/`)

Клиент не хранит расписание и не поднимает WiFi/веб-сервер — его единственная
задача: слушать LoRa, проверять подлинность команд и играть звук.

### 2.1 `main.cpp`

`setup()`: инициализация статусного светодиода (опционально, `STATUS_LED = -1`
в текущем `config.h` — выключен, т.к. GPIO33 занят под I2S DOUT), затем
`mp3_setup()`, `lora_setup()`.

`loop()` на Core 1: `lora_poll()` (разбор команд, пришедших из Core 0-очереди)
+ 8×`mp3_loop()` за итерацию — та же логика "частого кормления" аудио, что и
на сервере.

### 2.2 `lorahandler.cpp` — приём и верификация команд

Как и на сервере, вся радиоработа — в задаче `loraTask` на Core 0 (прерывание
DIO0 → `dioFlag` → чтение пакета).

**Верификация** (`verifyMsg`) применяется к GONG, HEARTBEAT и STOP:
1. Если в JSON нет поля `"sig"` — пакет отклоняется сразу (защита от
   произвольного, не от сервера, эфирного мусора).
2. Подпись пересчитывается локально (`computeHMAC`, тот же алгоритм и ключ,
   что на сервере) по телу без поля `sig` и сравнивается — несовпадение
   отклоняет пакет.
3. Replay-защита: у каждого сообщения есть `ts` (unix-время на момент
   отправки сервером). Клиент хранит `lastServerTs` — минимальный порог;
   принимаются только пакеты с `ts > lastServerTs`. Это не даёт злоумышленнику
   (или собственному эху LoRa) повторно "проиграть" перехваченный пакет.

`MSG_SCHEDULE` **не проверяется и не применяется** — клиент только логирует
факт получения (`Serial.printf("[LORA] Schedule received...")`). Расписание,
которое сервер рассылает через `/api/sync`, на сегодня не используется
клиентом — вероятно, задел на будущее (например, автономная работа клиента
при потере связи с сервером).

**ACK** (`sendAck`) отправляется на HEARTBEAT и GONG (не на STOP — остановка
не требует подтверждения) с 10–80 мс случайной задержкой (защита от коллизий
в эфире при одновременном ответе нескольких клиентов на broadcast).

**Разделение по ядрам**: `loraTask` (Core 0) сама шлёт ACK (не блокирует
аудио) и кладёт разобранную команду в `rxQueue`; `lora_poll()` на Core 1
вычитывает очередь и непосредственно дёргает `mp3_play()`/`mp3_stop()` —
аудио-библиотека не потокобезопасна между ядрами, поэтому весь доступ к ней
идёт только с Core 1.

### 2.3 `mp3handler.cpp`

Идентичен серверному модулю (§1.3): та же логика волюм-рампинга, то же ручное
зацикливание через `loopRemain`/`idleCount`. Отличие — `mp3_setup()` на
клиенте сам монтирует SPIFFS (`SPIFFS.begin(true)`), т.к. в клиенте нет
`main.cpp`-уровневой инициализации SPIFFS (в отличие от сервера, где это
делает `main.cpp` до вызова любых модулей).

## 3. Сквозные механизмы

### 3.1 Синхронизация звука сервер↔клиенты

И `onGongFire` (расписание), и `handlePlayAll` (ручной запуск из веб-интерфейса)
соблюдают порядок **"LoRa TX сначала, локальный плеер — после"**:
`lora_sendGong()` блокирует вызывающий код на `txGongDone` семафоре, то есть
физически ждёт, пока пакет полностью уйдёт в эфир (~170 мс на используемых
SF/BW). Только после этого стартует `mp3_play()` на сервере. Клиенты получают
и начинают играть трек сразу по приёму пакета. За счёт этого рассинхрон между
сервером и клиентами — это в основном разница в скорости запуска
MP3-декодера, а не в моменте отправки команды.

### 3.2 Безопасность LoRa-канала

- HMAC-SHA256 (усечённый до 64 бит) на каждом GONG/HEARTBEAT/STOP —
  подтверждает, что сообщение отправлено стороной, знающей `LORA_HMAC_KEY`.
- Монотонный `ts` — защита от replay.
- **Что не защищено**: сам факт того, что кто-то слушает эфир на 433 МГц и
  видит структуру трафика (не шифрование, а только аутентификация). SCHEDULE
  вообще не подписывается (см. §2.2) — сейчас это не критично, т.к. клиент его
  игнорирует.
- Ключ `LORA_HMAC_KEY` в `config.h` **должен совпадать** у сервера и у всех
  клиентов дословно — иначе клиент будет отбрасывать все команды с логом
  `Bad sig`.

### 3.3 Многопоточность (FreeRTOS, оба устройства)

Общий паттерн на сервере и клиенте:
- Core 0 = задача радио (создаётся `xTaskCreatePinnedToCore(..., 0)`),
  реагирует на прерывание DIO0, никогда не блокируется надолго.
- Core 1 = стандартный Arduino `loop()`, где `delay()`/блокирующие вызовы
  безопаснее, т.к. не мешают приёму пакетов.
- Обмен между ядрами — только через FreeRTOS-примитивы (`QueueHandle_t`,
  `SemaphoreHandle_t`), никогда напрямую через общие переменные без мьютекса
  (единственное исключение — `volatile bool dioFlag`, которое по контракту
  пишется только в ISR и читается только в `loraTask`, что безопасно без мьютекса).

### 3.4 Файлы на SPIFFS (сервер)

| Файл | Модуль | Назначение |
|---|---|---|
| `/wifi.conf` | webhandler | `{ssid, password}` для STA-подключения |
| `/auth.conf` | webhandler | `{enabled, password}` для веб-админки |
| `/gong.conf` | schedule | активное расписание (зеркало памяти `entries[]`) |
| `/dayNN.conf` (00–11) | schedule | сохранённые расписания по дням |
| `/activeday.conf` | schedule | `{day: N}` — какой день сейчас активен |
| `/000N.mp3` | mp3handler | аудио-треки, номер = `track` |
| `/index.html` + ассеты | webhandler | веб-интерфейс (SPA) |

Клиент хранит на SPIFFS только `/000N.mp3` — конфигов и расписания там нет.
