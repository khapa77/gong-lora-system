# Gong LoRa System — отчёт по аудиту

**Дата:** 23 августа 2026
**Объём проверки:** `server/` (10 файлов, ~1900 строк), `client/` (6 файлов, ~530 строк), `data/index.html` (41 КБ), `platformio.ini`, таблицы разделов, конфиги дней, `README.md`.
**Метод:** статический разбор исходников, сверка с документацией на SX1278 / MAX98357A / DS3231 / ESP32, расчёт времени в эфире LoRa, разбор поведения библиотек (RadioLib 6.6, ESP32-audioI2S 2.0.6, arduino-esp32 2.0.x).

## 0. Общее впечатление

Проект написан аккуратно: есть разделение по модулям, мьютексы вокруг небезопасного `Audio`, очереди между ядрами, HMAC-подпись команд, защита от overflow пула ArduinoJson, кольцевой буфер логов, корректная обработка coredump. Видно, что часть проблем уже находили и чинили — комментарии в коде это честно фиксируют.

Но есть **четыре блокирующих дефекта**, из-за которых система в реальной эксплуатации будет вести себя непредсказуемо, и **README описывает не ту систему, которая лежит в архиве**. Последнее — самое опасное: если собрать железо по README, оно не заработает, и причина будет неочевидна.

Сводка:

| Уровень | Кол-во | Суть |
|---|---|---|
| 🔴 Blocker | 4 | 5-секундные блокировки loop, замолкание клиентов после ребута сервера, коллизии ACK, бессмысленная метрика RTT |
| 🟠 High | 10 | ошибки в расчётах эфира, потеря пакетов, единая точка отказа, ключи по умолчанию, CORS, пароль в открытом виде |

### 1.2 GPIO — оценка выбора пинов

| Пин | Назначение | Оценка |
|---|---|---|
| GPIO5 | LoRa NSS | ⚠️ Strapping-пин (должен быть HIGH при старте). Внутренняя подтяжка есть, но на части плат GPIO5 выдаёт импульсы при загрузке. **Рекомендую внешний pull-up 10 кОм к 3.3 В на NSS**, чтобы SX1278 не видел мусорные транзакции пока ESP32 грузится |
| GPIO14 | LoRa RST | ⚠️ MTMS/JTAG, при загрузке выдаёт импульсы. Для RST безвредно (RadioLib всё равно ресетит модуль в `begin()`), но при длинных проводах возможен звон — 10 кОм pull-up + 100 нФ по месту |
| GPIO4 | LoRa DIO0 | ✅ Свободен, не strapping, ADC2 не используется. Правильный выбор |
| GPIO2 | (в README) | ❌ Strapping + встроенный синий светодиод на DevKit V1. Нагрузка светодиода на линию DIO0 + требование к уровню при загрузке. Правильно, что ушли |
| GPIO12 | не используется | ✅ Хорошо — это MTDI, задаёт напряжение flash |
| 18/19/23 | SPI SCK/MISO/MOSI | ✅ Штатный VSPI |
| 26/25/33 | I2S BCLK/LRC/DOUT | ⚠️ Функционально корректно (ADC2 не задействован). **Но GPIO32/33 на части плат разведены под внешний кварц 32.768 кГц.** Если плата с распаянным кварцем — DOUT на GPIO33 не заработает. Стоит проверить конкретную ревизию платы и записать в README |
| 21/22 | I2C для DS3231 | ✅ Штатные, конфликтов нет |
| STATUS_LED | `-1` (выключен) | ❌ **У клиента нет вообще никакой индикации.** Устройство без экрана, без сети, без кнопок. Понять «жив ли клиент, слышит ли он сервер» можно только подключив ноутбук по USB. Для железа, разбросанного по зданию, это серьёзный эксплуатационный минус |

### 1.3 MAX98357A — три реальные ошибки в схеме

**а) Вывод SD подключён напрямую к 3.3 В.**
У MAX98357A вывод SD одновременно и «шатдаун», и селектор канала — по уровню напряжения:

| Напряжение на SD | Режим |
|---|---|
| < 0.16 В | выключено |
| 0.16 … 0.77 В | **(L+R)/2 — моно-сумма** |
| 0.77 … 1.4 В | правый канал |
| > 1.4 В | левый канал |

Перемычка на 3.3 В = **только левый канал**. Внутри чипа есть подтяжка 100 кОм к земле. Для честного моно нужен **резистор 1 МОм от SD к VDD** — делитель 1 М / 100 к даст ~0.3–0.45 В, то есть режим (L+R)/2. Сейчас, если в MP3 полезное содержимое окажется в правом канале, вы его просто не услышите.

**б) Вывод GAIN нигде не задокументирован.**
Висящий GAIN = 9 дБ. Варианты: напрямую на GND — 15 дБ, через 100 кОм на GND — 12 дБ, висит — 9 дБ, через 100 кОм на VDD — 6 дБ, напрямую на VDD — 3 дБ. Для задачи «звонок должен быть слышен во всём здании» это ключевой параметр, а он не назван вообще.

**в) Питание усилителя от 5 В платы ESP32 — главный подозреваемый по стабильности.**
MAX98357A на 4 Ω при 5 В отдаёт до ~3.2 Вт, импульсный ток по питанию — **1.2…1.5 А**. Дорожки DevKit-платы, защитный диод и разъём USB на это не рассчитаны. Просадка при первом ударе гонга → brownout-детектор ESP32 → перезагрузка. Прямо в момент, когда звонок должен звучать.

Косвенное подтверждение: в `main.cpp` есть готовый код разбора coredump с комментарием, что предыдущая версия стирала дампы, «уничтожая единственное свидетельство сбоя». То есть падения были и их искали.

**Что нужно:** отдельный источник 5 В / 2–3 А, звезда по земле, **470–1000 мкФ + 0.1 мкФ прямо у VDD усилителя**, 100 мкФ + 0.1 мкФ у 3.3 В ESP32.

**г) Выход мостовой (BTL).** Ни один вывод динамика нельзя сажать на землю, нельзя объединять «минусы» двух усилителей. В README об этом ни слова — типичная ошибка при сборке.

**д) Класс D без выходного фильтра.** Провода к динамику — это антенна с широкополосным шумом на частоте коммутации (~300 кГц) и её гармониках. При длине более 1–2 м наведётся на приёмник 433 МГц, который стоит в том же корпусе. Витая пара или экран, ферритовая бусина на выходе.

### 1.4 SX1278 / Ra-02

1. **Питание 3.3 В берётся с AMS1117 платы DevKit.** Пик тока при TX +17 dBm — 90–120 мА, у сервера параллельно работает WiFi AP (пики до 300 мА). Линейник ток даст, но просадка на импульсе — вопрос ёмкостей. **100–220 мкФ + 100 нФ прямо у VCC модуля обязательны**, иначе TX будет ронять WiFi и наоборот.
2. **+20 dBm из README** — это отдельный режим PA_BOOST с требованием OCP ≥ 120 мА и **ограничением duty cycle 1%** по даташиту SX1278. В коде стоит 17 dBm — это правильнее. README нужно исправить, а не код.
3. **Регуляторика.** 433.05–434.79 МГц — ISM, но в ЕС (EN 300 220) типичный лимит — 10 мВт ERP и duty cycle 10%; в РФ по решению ГКРЧ на 433.075–434.775 МГц — 10 мВт. **+17 dBm = 50 мВт — превышение в 5 раз.** Это не программная проблема, но для стационарной установки в центре её стоит хотя бы зафиксировать письменно и осознанно принять.
4. **Антенна обязана быть подключена до подачи питания.** Работа PA на разомкнутый выход убивает модуль. Строки об этом в README нет.
5. **DIO1 не разведён.** Сейчас не требуется, но лишает возможности использовать CAD (Channel Activity Detection) и RX-timeout — а именно CAD нужен для нормального решения проблемы коллизий ACK (см. 2.3). **Рекомендую вывести DIO1 на свободный GPIO уже сейчас**, чтобы не переделывать платы потом.
6. **Размещение.** Антенну 433 МГц разносить от класс-D усилителя и от его проводов; корпус металлический — антенну наружу.

### 1.5 DS3231

- Пины 21/22 — корректно. У большинства готовых модулей подтяжки 4.7 кОм уже на плате.
- ❌ **README называет DS3231 «опциональным». Это неверно.** Сервер работает только как точка доступа, NTP в коде нет вообще. Без DS3231 время сбрасывается при каждом отключении питания, расписание блокируется (`ti.tm_year >= 124`), а автоматический переход по дням курса завязан на **календарную дату**. Для 12-дневного курса это значит: любое моргание света → оператор обязан вручную выставить дату и время, иначе расписание встанет намертво. **DS3231 — обязательный компонент.**
- ⚠️ **Батарейка.** В дешёвых модулях DS3231 стоит цепь подзарядки (резистор + диод) под LIR2032. Если поставить обычный CR2032, он будет постоянно «заряжаться» — вздутие, течь, в пределе разрушение модуля. Нужно либо выпаять зарядный резистор (обычно маркирован R5 / 201), либо ставить перезаряжаемый LIR2032. README рекомендует именно CR2032 — без оговорки это опасно.

### 1.6 Архитектура железа в целом

- **Нет OTA.** Таблица разделов: `app0 = 1.5 МБ` (factory), раздел `otadata` объявлен, но второй app-раздел отсутствует. Каждое обновление всех N клиентов — физически, с ноутбуком, к каждому устройству. Для распределённой системы в здании это большая эксплуатационная стоимость.
- **Нет внешнего супервизора питания**, нет доступной кнопки reset, нет индикации.
- Разделы заполняют ровно 4 МБ (`0x1b0000 + 0x250000 = 0x400000`) — корректно для стандартного модуля, но не оставляет ни байта запаса.

## 2. Логика программы — блокирующие дефекты

### 2.1 🔴 C-1. `getLocalTime()` блокирует главный цикл на 5 секунд

В arduino-esp32 сигнатура: `bool getLocalTime(struct tm* info, uint32_t ms = 5000)`. Внутри — цикл с `delay(10)`, который крутится **до 5 секунд**, пока год не станет больше 2016. Пока время не установлено, каждый вызов стоит 5 секунд.

Все пять мест вызова используют значение по умолчанию:

| Файл | Строка | Когда вызывается | Эффект при незаданном времени |
|---|---|---|---|
| `schedule.cpp` | 95 | `sched_check()` — **каждую секунду из `loop()`** | Главный цикл идёт со скоростью 0.2 Гц |
| `schedule.cpp` | 47 | `currentDateStr()` → `sched_activateDay(0)` в `setup()` | +5 с к загрузке |
| `lorahandler.cpp` | 326 | `lora_sendHeartbeat()` каждые 30 с | Блок Core 1 на 5 с |
| `webhandler.cpp` | 222 | `/api/status` | **Каждый опрос UI — 5 с** (UI дёргает его каждые 5 с) |
| `webhandler.cpp` | 168 | `/api/time` | Блок ровно в тот момент, когда пользователь **впервые задаёт время** |

**Состояние «время не задано» — это состояние по умолчанию** на любом устройстве без DS3231 и на любом устройстве после разряда батарейки RTC. В этом состоянии:

- веб-интерфейс отвечает по 5–10 секунд на запрос;
- кнопка «Set time» может отвалиться по таймауту браузера — а это единственный способ выйти из состояния;
- heartbeat уходит с многосекундной задержкой;
- всё выглядит как «зависание прошивки».

Скорее всего, именно это лечили механизмом `refreshInFlight` в `index.html` (комментарий там описывает «клики срабатывали минутами»). Лечили симптом.

### 2.2 🔴 C-2. Anti-replay глушит связь на срок до часа после каждой перезагрузки сервера

`server/src/lorahandler.cpp:113`:
```cpp
static uint32_t nowTs() {
    time_t t = time(nullptr);
    return (t > 100000UL) ? (uint32_t)t : (uint32_t)(millis() / 1000);
}
```
Когда системное время не задано, метка `ts` = uptime в секундах. Она **не монотонна между перезагрузками**.

Клиент (`client/src/lorahandler.cpp:61`) хранит `lastServerTs` и отбрасывает пакет, если `ts` откатился меньше чем на `REPLAY_RESYNC_GAP_S = 3600`.

**Сценарий отказа:**
1. Сервер работает 25 минут → `ts ≈ 1500`, клиент запомнил `lastServerTs = 1500`.
2. Сервер перезагружается (моргнуло питание) → `ts` снова начинается с 0.
3. Клиент видит `ts = 5`, откат `1495 < 3600` → **`Replay ts=5 last=1500 — rejected`**.
4. Пакеты отбрасываются, пока uptime сервера снова не превысит 1500 с — то есть **до 25 минут полной глухоты**.

Порог 3600 с делает ситуацию хуже, а не лучше: спасает он только тогда, когда сервер до сбоя проработал **больше** часа. То есть логика защищает от редкого случая и ломается на частом.

Симптом в поле: «после перезагрузки сервера часть гонгов не проходит». В serial клиента строчка есть, но клиента никто не слушает — светодиод отключён (см. 1.2).

Дополнительно: клиент не сохраняет `lastServerTs` в NVS. После своей перезагрузки он принимает **любой** ранее записанный в эфире пакет один раз — anti-replay в этот момент нулевой.

### 2.3 🔴 C-3. Коллизии ACK: система нерабочая при более чем 1–2 клиентах

Клиент отвечает на HEARTBEAT и на GONG через `vTaskDelay(pdMS_TO_TICKS(10 + random(0, 70)))` — **окно разброса 70 мс**.

Реальное время в эфире при текущих параметрах (SF9, BW125 кГц, CR 4/5, преамбула 8, explicit header):

| Пакет | Размер | SF9 (сейчас) | SF8 | SF7 |
|---|---|---|---|---|
| ACK `{"id":"...","rssi":-52,"hb":12}` | ~41 Б | **288 мс** | 158 мс | 87 мс |
| GONG с подписью | ~72 Б | **431 мс** | 236 мс | 133 мс |
| HEARTBEAT с подписью | ~76 Б | **452 мс** | 246 мс | 139 мс |

**Окно джиттера (70 мс) в четыре раза меньше длительности одного ACK (288 мс).**
Следствие: при двух и более клиентах ACK-и накладываются практически всегда. Сервер услышит один за счёт эффекта захвата или ни одного.

Наблюдаемое поведение: клиенты «мигают» в панели LoRa Clients, `lora_clientCount()` скачет, поле `clients` в heartbeat врёт, RTT — мусор.

Отдельно: **ACK на GONG не нужен вообще.** Сервер явно его игнорирует для RTT (`if (hb != 0 …)`), а в эфир он уходит ровно в тот момент, когда клиент должен запускать звук — и держит радио занятым ~290 мс, в течение которых клиент не может принять STOP.

### 2.4 🔴 C-4. Метрика RTT / OneWay физически бессмысленна

README: *«Позволяют оценить качество связи и расстояние до каждого клиента»*.

Задержка распространения радиоволны на 1 км — **3.3 микросекунды**. Измеряемый RTT состоит из времени в эфире ACK (~288 мс) плюс джиттера (~45 мс). Это на **пять порядков** больше полезного сигнала.

`oneWay = (RTT − 45) / 2 ≈ 145 мс` — это ровно половина airtime ACK. Одно и то же число для клиента в соседней комнате и для клиента в километре. Метрика измеряет собственные настройки модема, а не канал.

Показатели, которые действительно что-то говорят о линке — **RSSI и SNR**. `radio.getSNR()` в коде не вызывается ни разу, хотя для LoRa SNR информативнее RSSI (он показывает запас до порога демодуляции и уходит в минус до −20 дБ).

## 3. Логика программы — важные дефекты (High)

### H-1. Комментарии о времени в эфире занижены втрое
`lora_sendGong()`: *«At SF9 this is ~100-150ms, inaudible as a delay»*. Реально — **431 мс**. То есть `lora_sendGong()` блокирует главный цикл Core 1 почти на полсекунды (а при таймауте DIO0 — до 4 секунд, `TX_TIMEOUT_MS = 4000`). Всё это время не обслуживается HTTP и не проверяется расписание.

### H-2. Потеря пакета в окне джиттера ACK
`client/src/lorahandler.cpp:100–112`:
```cpp
vTaskDelay(pdMS_TO_TICKS(10 + random(0, 70)));  // радио ещё в RX
...
dioFlag = false;                                 // ← сбрасывает флаг вслепую
radio.startTransmit(buf, 1 + plen);
```
Если во время джиттера прилетел пакет (например, STOP сразу после GONG), его флаг сбрасывается и **пакет теряется бесследно** — ни в логе, ни в счётчиках.

### H-3. Нет привязки к «сессии» сервера
Даже после починки C-2 порогом остаётся проблема: клиент, перезагрузившись, обнуляет `lastServerTs` и принимает старую запись из эфира. Нужен boot-id или счётчик, переживающий перезагрузку у обеих сторон.

### H-4. Нет никакой деградации при отказе радиоканала
Заглушить 433 МГц дешёвым передатчиком — тривиально. Клиент без сервера полностью нем: расписания у него нет (`MSG_SCHEDULE` удалён), локального времени нет. README это честно фиксирует, но решения не предлагает.

### H-5. 🔴 по факту — сервер единая точка отказа
Сервер умер ночью → **утренний подъём в 04:00 не прозвонит нигде.** Для 12-дневного ретрита, где распорядок и есть суть мероприятия, это самый тяжёлый операционный риск во всём проекте.

При этом решение существует и дешёвое: расписание дня — 16 записей × 4 байта (час, минута, трек, повторы) = **64 байта**. Это спокойно влезает в один LoRa-кадр, если использовать бинарный формат вместо JSON (JSON того же расписания — 1.8 КБ, отсюда и вывод «не влезает»). См. документ с решениями.

### H-6. Дубликаты `CLIENT_ID` никак не отслеживаются
Дефолт в репозитории — `"client_twoX"`. Забыли поменять на втором устройстве → в реестре сервера один клиент, RSSI скачет, реальное количество неизвестно. Никакой проверки нет.

### H-7. HMAC-ключ по умолчанию лежит в репозитории
`"change_me_before_deploy_32chars!"` в обоих `config.h`. Забыли поменять → подпись бесполезна: любой, у кого есть Ra-02 и этот репозиторий, может звонить в гонг в три часа ночи. Ни проверки при сборке, ни предупреждения в рантайме нет.

### H-8. `/api/sync` — мёртвая кнопка в интерфейсе
`handleSync()` всегда возвращает `400`, но кнопка «⟳ Sync Schedule» осталась на панели. Оператор жмёт → красный тост «Error». Это приучает игнорировать ошибки — а потом будет проигнорирована настоящая.

### H-9. Wildcard CORS с preflight на админ-API
`Access-Control-Allow-Origin: *` + обработчики `OPTIONS` + `Allow-Headers: Content-Type` означают, что **любая веб-страница**, открытая на устройстве, подключённом к точке доступа, может выполнить
```js
fetch('http://192.168.4.1/api/play/all', {method:'POST', headers:{'Content-Type':'application/json'}, body:'{"track":1,"vol":30}'})
```
и позвонить в гонг. Аутентификация по умолчанию выключена. Риск в изолированной AP невысокий, но **CORS здесь не нужен вообще** — интерфейс отдаётся с того же origin.

### H-10. Пароль админки хранится открытым текстом
`/auth.conf`: `{"enabled":true,"password":"..."}`. Дамп flash (или заливка своей прошивки-дампера) — и пароль в руках. Плюс Basic Auth поверх HTTP, плюс сравнение не константное по времени. mbedTLS уже подключён — хэш стоит ноль дополнительных зависимостей.

## 6. Дублирование кода между сервером и клиентом — системный риск

`mp3handler.cpp` совпадает на ~95 %, функция `computeHMAC()` — дословно, RF-параметры продублированы в двух `config.h`.

**Критично, что продублированы именно эти константы:**
```
LORA_FREQ, LORA_SF, LORA_BW, LORA_CR, LORA_SYNC_WORD, LORA_HMAC_KEY
```
Они **обязаны совпадать**, иначе устройства просто не слышат друг друга — без единого сообщения об ошибке. Комментарий в клиентском конфиге это признаёт: *«MUST match the server's config.h exactly, or the devices will simply never hear each other (no error, just silence)»*.

И при этом сейчас они уже расходятся с README (SF9 против SF7, 17 dBm против 20 dBm). Достаточно одному человеку поправить один файл — и половина парка замолчит.

Проверки на этапе сборки нет. Проверки в рантайме нет. Это самая вероятная причина будущего долгого разбора «почему один клиент не звонит».

## 7. Что работает хорошо

Чтобы картина была честной:

- Мьютекс вокруг `Audio` — правильное и неочевидное решение, комментарий точно описывает причину.
- Очередь Core 0 → Core 1 на клиенте и порядок «сначала в очередь, потом ACK» — грамотно, даёт хорошую синхронность старта звука.
- Защита от overflow пула ArduinoJson с отказом писать на диск — предотвращает реальную потерю данных.
- Дренаж «протухшего» токена `txGongDone` перед ожиданием — тонкий момент, найден и закрыт.
- Учёт RTT только по ACK с эхом `seq` последнего heartbeat — концептуально верно (проблема не в этом, а в том, что сама метрика бессмысленна).
- Разбор coredump до стирания.
- Разделение «активный день» / «шаблон дня» с единым источником истины через делегирование в `sched_add/edit/del` — аккуратно.
- Исправление знаковости `char` при экранировании UTF-8 в логах — редкая и полезная находка.
- `refreshInFlight` в UI.
