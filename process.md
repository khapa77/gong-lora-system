# Логика расписания (schedule.cpp / webhandler.cpp)

Разбор актуального (WiFi-only, ветка `only_wifi`) состояния сервера: как хранится
расписание, как переключаются "дни курса", что происходит в 23:59→00:00 и что
происходит, когда дни расписания заканчиваются (после day11).

Контекст: судя по `shedule` (референс) и `server/data/day00..11.conf`, это
таймлайн 10-дневного курса Випассаны: **day00 = день заезда**, **day01–day10 =
одинаковый "боевой" распорядок курса**, **day11 = день отъезда** (day00 и day11
побайтово совпадают друг с другом и с эталонным `shedule`). "День" — это номер
дня курса, а не день недели и не календарная дата.

## 1. Модель данных

- `/gong.conf` — **активное** расписание, которое реально проверяется в рантайме
  (массив `ScheduleEntry entries[MAX_SCHEDULES]`, максимум 32 записи).
- `/day00.conf` … `/day11.conf` — 12 "шаблонов дня" (фиксированный диапазон,
  захардкожен как 0–11 в трёх местах: `webhandler.cpp:267`, `:274` и
  во фронтенде `index.html:754`).
- `/activeday.conf` — `{"day": N}`, какой шаблон сейчас активен. Если файла нет —
  `sched_getActiveDay()` возвращает `-1` ("день не выбран").
- Каждая запись: `{id, hour, min, track, loop, en(abled), desc}`.

Важно: `/gong.conf` — не отдельная сущность, это просто зеркало активного
`/dayNN.conf`. Любое изменение через `/api/schedule` (add/edit/delete)
одновременно пишется и в `/gong.conf`, и в файл текущего активного дня
(`sched_save()`, schedule.cpp:162-180) — если активный день установлен
(`sched_getActiveDay() >= 0`).

## 2. Проверка расписания — раз в секунду (`sched_check`)

Вызывается из `main.cpp:56` каждую секунду (не каждый тик loop).

1. Читает системное время (`getLocalTime`). Если время не установлено
   (RTC не отдал валидное время и ручное время не задано) — выходит, ничего
   не делает (лог раз в 60 c).
2. Считает, что время валидно, только если `tm_year >= 124` (реальная дата
   с 2024 года) — специально отсекает состояние "ESP32 включился, системные
   часы = 1970, но `getLocalTime()` уже не возвращает false".
3. **Полночь / переключение дня** (h==0 && m==0, с защитой от повторного
   срабатывания в течение 65 c):
   - Если активный день не установлен (`activeDay == -1`) — **ничего не
     происходит**. Переключение дней вообще не запускается, пока хотя бы раз
     не была явная активация дня через UI/API.
   - Если активный день установлен — пробуем `/day(N+1).conf`. Если файл
     существует — переключаемся (`sched_activateDay`). Если файла нет
     (после day11 это `/day12.conf`, которого нет) — **ничего не происходит**,
     день остаётся тем же навсегда.
4. **Срабатывание гонга**: линейный проход по записям активного дня; первая
   запись, у которой `enabled && hour==h && minute==m`, запускает
   `onScheduleTrigger(track, loop)` и `break` (одна запись в минуту, даже если
   таких записей несколько на одно и то же время — сработает только первая
   по порядку в массиве).
5. Anti-double-trigger: `lastFiredKey`/`lastFiredMillis` — не даёт повторно
   сработать в течение 65 c для той же минуты (запас от джиттера NTP/RTC).
   Общий на все записи, не per-entry.

## 3. Переключение дня (`sched_activateDay`)

1. Если `/dayN.conf` не существует — создаёт его. Если это вообще первая
   активация за всё время (`activeday.conf` ещё не было) — сидирует новым
   файлом **текущее** содержимое `/gong.conf` (чтобы не потерять то, что уже
   было). Если активация не первая — новый день создаётся **пустым** (`[]`).
2. `sched_save()` — сбрасывает текущее (ещё старое) расписание в его файл
   дня, пока `/activeday.conf` ещё указывает на старый день.
3. Загружает новый `/dayN.conf` в память.
4. Пишет содержимое нового дня в `/gong.conf` напрямую (не через `sched_save`,
   иначе он затёр бы файл нового дня файлом старого — `activeday.conf` в этот
   момент ещё не обновлён).
5. Обновляет `/activeday.conf` на новый номер.

Вызывается из двух мест:
- `sched_check()` при пересечении полуночи (автоматически).
- `handleDayActivate()` — `POST /api/day/activate?n=N` (вручную, из UI).

## 4. Что происходит в 23:59 → 00:00

- В 23:59 никакого специального действия нет — это обычная минута, гонг
  срабатывает, если на неё есть запись.
- В 00:00:00 (первая секунда, когда `sched_check()` увидит h=0,m=0):
  - если активный день задан и `/day(N+1).conf` существует — день
    переключается **до** прохода по записям на срабатывание, поэтому если у
    нового дня есть запись на 00:00, она сработает уже по-новому дню;
  - если активного дня нет или следующего файла нет — просто продолжает
    работать текущее расписание, как в любую другую минуту.
- Условие переключения — не "дата изменилась", а буквально "часы:минуты
  сейчас равны 00:00". Если устройство было выключено/перезагружалось именно
  в этот момент (пропустило единственный тик 00:00 суток), автоматическое
  переключение **на эти сутки не произойдёт вообще** — код не сравнивает
  "какой сегодня день" с "какой день должен быть", он реагирует только на
  живое пересечение полуночи. Подробнее — в task.md.

## 5. Что происходит, когда дни расписания заканчиваются (после day11)

- Диапазон дней жёстко ограничен 0–11 (12 шаблонов = 12 дней курса).
- Когда активный день = 11 и наступает полночь, код ищет `/day12.conf`.
  Такого файла нет и никогда не создаётся автоматически (диапазон 0-11
  зашит в `handleDayActivate`/`handleDayGet`, так что и вручную через API
  создать `day12` нельзя).
- **Результат: day11 остаётся активным бессрочно.** Гонг продолжает звонить
  по расписанию дня отъезда (day11 = day00, "лёгкий" распорядок с отбоем в
  21:30) каждый день, пока кто-то вручную не активирует `day00` через UI
  (стрелка навигации или прямой вызов `/api/day/activate?n=0`) для нового
  заезда.
- Автоматического "закольцовывания" на `day00` нет. Нет и уведомления в UI о
  том, что курс закончился и пора вручную сбросить на день 0 — просто тихо
  продолжает греметь day11 каждый день.

## 6. Проверка условий (прогон по коду)

| # | Условие | Реализовано? | Комментарий |
|---|---|---|---|
| 1 | Время не установлено → расписание не проверяется | ✅ | `sched_check()` ранний выход, лог раз в 60с |
| 2 | Ложная "нулевая" дата (1970/2024 boot) не триггерит | ✅ | проверка `tm_year >= 124` |
| 3 | Гонг звонит один раз в минуту, не повторяется | ✅ | `lastFiredKey`/65с окно |
| 4 | Несколько записей на одно и то же hh:mm | ⚠️ частично | сработает только первая по порядку массива, остальные молча пропускаются — `break` в цикле, schedule.cpp:95 |
| 5 | Смена дня в полночь, если следующий файл есть | ✅ | schedule.cpp:64-77 |
| 6 | Смена дня в полночь, если следующего файла нет | ✅ (по замыслу — "стоп на последнем дне") | но без индикации/уведомления — см. task.md |
| 7 | Смена дня, если `activeDay == -1` (день никогда не активировался) | ❌ не работает | `if (activeDay >= 0)` — авто-переключение попросту выключено, пока оператор явно не активирует день хотя бы раз |
| 8 | Реакция на пропущенную полночь (перезагрузка/отключение питания ровно в 00:00) | ❌ не работает | нет сравнения "текущая дата vs дата последнего переключения", есть только живой тик h=0,m=0 |
| 9 | Изменения расписания (add/edit/delete) сохраняются и в `/gong.conf`, и в файл активного дня | ✅ | `sched_save()`, зеркалирование |
| 10 | Валидация часа/минуты/трека/loop на входе (add/edit) | ✅ | обрезка/отказ в `sched_add`/`sched_edit`, совпадает с фронтом |
| 11 | Диапазон дней 0–11 валидируется одинаково везде | ✅ | backend (`webhandler.cpp`) и frontend (`index.html:754`) оба используют 0–11 |
| 12 | Переполнение `MAX_SCHEDULES` (32 записи) | ✅ обработано | `sched_add` отказывает при `count>=MAX_SCHEDULES`; `sched_parseFromPath` молча обрезает лишнее при загрузке дня |
| 13 | Циклический возврат на day00 после day11 | ❌ отсутствует | см. раздел 5 — фича либо не реализована, либо реализована "не автоматически, а руками", не задокументировано ни в коде, ни в UI |

Итог: базовая логика "минута наступила → проверить записи → сработать один раз"
реализована корректно и надёжно. Слабое место — весь механизм многодневного
расписания (переключение по дням курса): он не активируется сам по себе, не
переживает пропуск полуночи и не знает, что делать после последнего дня.
Детали — в `task.md`.
