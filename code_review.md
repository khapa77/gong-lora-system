## Что сделано хорошо

Чтобы не создавать ложного впечатления: база у проекта здоровая.

- **Архитектура LoRa v3** — вынос радио в отдельный таск на Core 0, прерывание на DIO0 вместо поллинга, FreeRTOS-очередь между ядрами. Это правильный ответ на проблему длинного TX при SF12.
- **Мьютекс на список клиентов** — доступ из двух ядер защищён корректно, вложенных захватов нет, дедлока не будет.
- **HMAC-SHA256 на командных пакетах** через встроенный mbedTLS, без лишних зависимостей. Сама схема (подпись типа + payload, sig дописывается последним полем) рабочая — порядок полей ArduinoJson сохраняет, ресериализация на клиенте даёт байт-в-байт тот же payload.
- **Большие JSON вынесены в кучу** (`sched_toJSON`, `sched_parseFromPath`) — стек ESP32 они бы переполнили.
- **DS3231 как fallback** и приоритет источников времени — правильная идея для системы, которая должна звонить по расписанию без интернета.
- **`docs/lora-signal-research.md`** — редкая и по-настоящему полезная вещь: история конфигураций с обоснованиями и открытые вопросы по железу.
- **Данные консистентны**: все 13 файлов `day*.conf` + `gong.conf` — валидный JSON по 16 записей; MP3 на сервере и клиенте совпадают по MD5; таблица разделов сходится ровно в 4 МБ (1.5 МБ app + 2.55 МБ SPIFFS).

## 🔴 Критично

### C1 — В репозитории лежат рабочие секреты

**Где:** `server/data/wifi.conf`, `server/include/wifi.conf`, `server/src/config.h:55`, `client/src/config.h:41`

```
server/include/wifi.conf : dd-wrt50 / 81374287
server/data/wifi.conf    : {"ssid":"dd-wrt50","password":"81374287"}
config.h (оба)           : #define LORA_HMAC_KEY "!vK7#2xM"
```

Пароль от WiFi в публичном репозитории с коммита `8b219a8`. HMAC-ключ — 8 символов при том, что README требует минимум 16; он в истории с коммита `20a95cc`. Удаление файлов из рабочего дерева не поможет — они остаются в истории.

**Побочный эффект:** `server/data/` заливается в SPIFFS через `pio run -t uploadfs`, то есть `wifi.conf` физически попадает на устройство. Описанный в README сценарий первого запуска («нет `wifi.conf` → поднимается AP `GongServer`») не отработает никогда. Туда же попадает `.DS_Store` (6 КБ мусора).

**Фикс:** сменить пароль на роутере и HMAC-ключ, вычистить историю, вынести секреты в некоммитируемый `secrets.ini` → `build_flags`.

### C2 — Replay-защита блокирует нормальную работу

**Где:** `server/src/lorahandler.cpp:109-112` (`nowTs`), `client/src/lorahandler.cpp:40,55-60` (`verifyMsg`)

```cpp
// server
static uint32_t nowTs() {
    time_t t = time(nullptr);
    return (t > 100000UL) ? (uint32_t)t : (uint32_t)(millis() / 1000);
}

// client
static uint32_t lastServerTs = 0;
...
uint32_t ts = doc["ts"] | 0;
if (ts > 0 && ts <= lastServerTs) { /* rejected */ return false; }
```

Один общий счётчик на все типы сообщений, разрешение — одна секунда.

**Следствие 1 — Stop не работает.** Нажали Play, тут же Stop: у STOP тот же `ts`, что у GONG → условие `ts <= lastServerTs` срабатывает → пакет отброшен. Клиент продолжает играть. То же с любыми двумя командами в одну секунду.

**Следствие 2 — сервер не переживает перезагрузку.** Если часы не выставлены, `nowTs()` возвращает `millis()/1000`, то есть десятки. Клиенты, которые до ребута видели unix-время (~1.7e9), после перезагрузки сервера режут **все** пакеты. В AP-режиме без DS3231 NTP не появится никогда → система мертва до ручного ребута всех клиентов. При этом README обещает, что ручное управление в AP-режиме работает.

**Фикс:** заменить `ts` на пару `boot` + `seq`.

```cpp
// server: при старте
static uint16_t bootId;              // esp_random() в lora_setup()
static uint32_t txSeq = 0;           // инкремент в loraSend() для подписанных типов

doc["boot"] = bootId;
doc["seq"]  = ++txSeq;
doc["ts"]   = nowTs();               // оставить для информации/логов

// client
static uint16_t lastBoot = 0;
static uint32_t lastSeq  = 0;
static bool haveState    = false;

uint16_t boot = doc["boot"] | 0;
uint32_t seq  = doc["seq"]  | 0;
if (haveState && boot == lastBoot && seq <= lastSeq) return false;  // replay
lastBoot = boot; lastSeq = seq; haveState = true;
```

Смена `boot` означает перезагрузку сервера — состояние сбрасывается. Внутри одной сессии `seq` строго монотонный, разрешение — один пакет, а не одна секунда. Остаточный риск: атакующий может переиграть пакет, пойманный до перезагрузки сервера, — для этой модели угроз приемлемо.

### C3 — Падение при неудачной инициализации LoRa

**Где:** `server/src/lorahandler.cpp:237-250`, `client/src/lorahandler.cpp:179-189`

```cpp
int state = radio.begin(...);
if (state != RADIOLIB_ERR_NONE) {
    Serial.printf("[LORA] Init FAILED: %d — check module wiring!\n", state);
    return;                      // ← выход ДО создания очередей
}
txQueue    = xQueueCreate(2, sizeof(TxReq));
clientsMtx = xSemaphoreCreateMutex();
```

При ошибке `txQueue`, `txGongDone`, `clientsMtx` (сервер) и `rxQueue` (клиент) остаются `nullptr`. Дальше:

- сервер, через 30 с: `lora_sendHeartbeat()` → `uxQueueMessagesWaiting(nullptr)`;
- сервер, при первом же запросе к веб-UI: `lora_clientCount()` → `xSemaphoreTake(nullptr, portMAX_DELAY)`;
- клиент, в первой же итерации `loop()`: `lora_poll()` → `xQueueReceive(nullptr, ...)`.

Всё это упирается в `configASSERT` → `abort()` → бутлуп. Ваш собственный `fail.txt` фиксирует именно этот сценарий: `[LORA] Init FAILED: -8` (`RADIOLIB_ERR_CHIP_NOT_FOUND`), затем «Listening for server commands...» и мусор в консоли.

**Фикс:** создавать примитивы синхронизации **до** `radio.begin()`, добавить `static volatile bool loraOk` и ранний выход по нему во всех публичных функциях. Отдельно стоит добавить повтор инициализации раз в 10 секунд — обрыв по питанию модуля не должен требовать ребута контроллера.

### C4 — `getLocalTime()` вешает loop() на 5 секунд

**Где:** `server/src/schedule.cpp:35`, `server/src/lorahandler.cpp:285`, `server/src/webhandler.cpp:275`

Сигнатура в arduino-esp32: `bool getLocalTime(struct tm* info, uint32_t ms = 5000)`. Внутри — цикл `while((millis()-start) <= ms)` с `delay(10)`, возврат только когда `tm_year > 116` либо по таймауту.

Во всех трёх местах второй аргумент не передан. `sched_check()` вызывается **раз в секунду** из `loop()`. Пока время не установлено (AP-режим, или первые 1–2 минуты до NTP-синхронизации) каждый вызов блокирует основной цикл на 5 секунд:

- `mp3_loop()` не вызывается → underrun буфера I2S, звук заикается;
- `web_loop()` не вызывается → веб-интерфейс не отвечает;
- heartbeat уезжает по времени.

**Фикс:** одна правка в трёх местах.

```cpp
if (!getLocalTime(&ti, 0)) { ... }   // не блокировать
```

Или свой хелпер:

```cpp
static bool timeNow(struct tm* ti) {
    time_t t = time(nullptr);
    if (t < 1700000000UL) return false;
    localtime_r(&t, ti);
    return true;
}
```

### C5 — Часовой пояс не выставляется без STA-подключения

**Где:** `server/src/main.cpp:40-44`, `server/src/webhandler.cpp:438`, `server/src/rtchandler.cpp:31-34`

`configTime()` — единственное место в проекте, где устанавливается TZ (внутри она вызывает `setTimeZone(-gmtOffset_sec, ...)`). Вызывается она только здесь:

```cpp
// webhandler.cpp, wifi_connect(), ТОЛЬКО при успешном коннекте:
configTime(NTP_UTC_OFFSET, 0, NTP_SERVER);
```

Порядок в `setup()`: `rtc_setup()` → ... → `web_setup()`. То есть `rtc_setup()` кладёт в системные часы UTC-epoch из DS3231 **до** того, как TZ вообще может быть установлен. А если устройство поднялось в AP-режиме, `configTime` не вызовется никогда → TZ остаётся UTC → `getLocalTime()` возвращает UTC.

**Следствие:** расписание срабатывает со сдвигом на `NTP_UTC_OFFSET` (сейчас 3 часа). Причём именно в том сценарии, ради которого DS3231 и ставился — «перезагрузка без WiFi, RTC помнит время».

**Фикс:** выставлять TZ безусловно и первым делом.

```cpp
void setup() {
    Serial.begin(115200);
    ...
    setenv("TZ", "UTC-3", 1);   // либо configTzTime; знак инвертирован — POSIX
    tzset();
    rtc_setup();
    ...
}
```

Лучше завести в `config.h` `#define TZ_STRING "UTC-3"` рядом с `NTP_UTC_OFFSET`, чтобы они не разъехались.

### C6 — `/api/sync` не работает в принципе

**Где:** `server/src/lorahandler.cpp:115-138,301-304`, `client/src/lorahandler.cpp:161-163`

```cpp
#define LORA_PAYLOAD_MAX 256
...
size_t plen = finalPayload.length();
if (plen > LORA_PAYLOAD_MAX) plen = LORA_PAYLOAD_MAX;
req.len = 1 + plen;                       // → 257
```

Предел SX127x — 255 байт (`RADIOLIB_SX127X_MAX_PACKET_LENGTH`), `startTransmit()` вернёт `RADIOLIB_ERR_PACKET_TOO_LONG`. Текущий `gong.conf` сериализуется в ~1748 байт, то есть эндпоинт не срабатывает никогда.

Даже если бы пакет ушёл — клиент на `MSG_SCHEDULE` только печатает количество байт и ничего с ними не делает. При этом UI показывает «Schedule sent to all clients».

**Фикс:** решить, нужна ли фича вообще. Клиент часов не имеет и локальное расписание исполнять не может, так что пересылка ему расписания смысла не несёт. Рекомендация — **удалить** `/api/sync`, кнопку «Sync Schedule» и `MSG_SCHEDULE`. Если фича нужна на будущее (автономный режим клиента при пропаже сервера) — это отдельная задача: фрагментация, сборка, часы на клиенте.

Независимо от решения — `LORA_PAYLOAD_MAX` надо снизить до 254 и добавить проверку с логом вместо тихого обрезания.

## 🟠 Серьёзно

### S1 — Коллизии ACK при нескольких клиентах

**Где:** `client/src/lorahandler.cpp:80`

```cpp
vTaskDelay(pdMS_TO_TICKS(10 + random(0, 70)));  // collision avoidance
```

Окно рандомизации — 70 мс. Время в эфире самого ACK (~40 байт payload) при текущих SF7 / BW 125 кГц / CR 4/8:

| | |
|---|---|
| Длительность символа | 128 / 125000 = 1.024 мс |
| Преамбула (8 + 4.25 симв.) | ~12.5 мс |
| Payload (104 симв.) | ~106 мс |
| **Итого ToA** | **~119 мс** |

Окно (70 мс) существенно **уже** длительности пакета (119 мс) → при двух и более клиентах ACK гарантированно перекрываются, сервер не декодирует ни один. README обещает «любое количество клиентов»; фактически надёжно работает один. При возврате к SF12/BW31.25, который стоит в планах в `docs/lora-signal-research.md`, ситуация становится безнадёжной (ToA ACK — секунды).

**Фикс:** детерминированные слоты вместо рандома.

```cpp
// ширину слота считать от текущих RF-настроек, не хардкодить
static uint32_t ackSlotMs() {
    return (uint32_t)(radio.getTimeOnAir(48) / 1000) * 13 / 10 + 20;  // ToA + 30% + запас
}
static uint8_t mySlot() {                 // стабильный слот из CLIENT_ID
    uint32_t h = 5381;
    for (const char* p = CLIENT_ID; *p; p++) h = h * 33 + (uint8_t)*p;
    return h % MAX_CLIENTS_EXPECTED;      // напр. 8
}
...
vTaskDelay(pdMS_TO_TICKS(20 + mySlot() * ackSlotMs()));
```

`MAX_CLIENTS_EXPECTED` держать небольшим (8), иначе полный цикл ACK растянется. При 8 слотах по ~175 мс это ~1.4 с после каждого heartbeat — на интервале 30 с приемлемо.

### S2 — Клиент стартует звук позже сервера

**Где:** `client/src/lorahandler.cpp:149-157`, комментарий `server/src/main.cpp:19-23`

```cpp
// main.cpp (server) обещает:
// Send LoRa FIRST (blocking TX ~170ms), then start local playback.
// Both server and client will begin audio after TX completes → in sync.

// client/lorahandler.cpp — фактически:
sendAck(rssi);                       // 10–80 мс задержки + ~119 мс передачи
xQueueSend(rxQueue, &cmd, 0);        // только потом воспроизведение
```

Сервер стартует звук сразу по завершении TX, клиент — после отправки собственного ACK. Отставание **130–200 мс**. Для гонга в соседних помещениях это отчётливо слышимый «флэм», а вся конструкция с блокирующим `xSemaphoreTake` в `lora_sendGong()` затевалась именно ради синхронности.

**Фикс:** поменять две строки местами.

```cpp
xQueueSend(rxQueue, &cmd, 0);        // сначала звук
sendAck(rssi);                       // потом ACK
```

Полностью синхронизации это не даст (Core 1 подхватит команду в течение итерации `loop()`), но остаточная разница уйдёт в единицы миллисекунд. Радикальный вариант — см. S3.

### S3 — `lora_sendGong()` блокирует Core 1

**Где:** `server/src/lorahandler.cpp:264-265`

```cpp
// Block Core 1 until TX completes — both sides start audio after TX
xSemaphoreTake(txGongDone, pdMS_TO_TICKS(30000));
```

Вызывается из `sched_check()` (то есть из `loop()`) и из HTTP-хендлеров `/api/play/lora`, `/api/play/all`. На время передачи не работают ни `mp3_loop()`, ни `web_loop()`.

| Конфигурация | ToA GONG (~60 байт) | Что происходит |
|---|---|---|
| SF7 / 125 кГц (текущая) | ~150 мс | Заметный дроп звука, если что-то играло |
| SF10 / 62.5 кГц | ~1.2 с | Веб «залипает», звук рвётся |
| SF12 / 31.25 кГц (в планах) | **~20 с** | Полная заморозка; ещё чуть-чуть — и упрётся в таймаут 30 с |

То есть заявленная в `docs/lora-signal-research.md` «полная изоляция LoRa на Core 0» этой одной строкой и обнуляется.

**Фикс:** не блокировать, а синхронизировать по общему дедлайну. Сервер до передачи считает время в эфире и планирует собственный старт на тот же момент, когда его услышит клиент:

```cpp
void lora_sendGong(uint8_t track, uint8_t vol, uint8_t loop) {
    ...
    loraSend(MSG_GONG, s);                 // не ждём
    uint32_t toa = radio.getTimeOnAir(payloadLen) / 1000;
    schedulePendingPlay(track, vol, loop, millis() + toa + TX_QUEUE_MARGIN_MS);
}
```

и в `loop()` проверять `pendingPlayAt`. Клиент стартует по факту приёма (после правки S2), сервер — по расчётному моменту. Расхождение уложится в десятки миллисекунд, а веб и звук продолжают работать всё время передачи.

### S5 — RTT/one-way считается неправильно

**Где:** `server/src/lorahandler.cpp:210-219`, `upsertClient():56-64`

```cpp
if (msgType == MSG_ACK) {
    uint32_t rtt = (lastHeartbeatSentMs > 0)
                   ? (uint32_t)(millis() - lastHeartbeatSentMs) : 0;
```

**Проблема 1 — загрязнение.** Клиент отправляет ACK не только на HEARTBEAT, но и на GONG. Сервер же считает RTT относительно последнего heartbeat всегда. ACK на ручной Play, пришедший через 20 с после heartbeat, даёт `rtt = 20000` мс, и это значение заезжает в экспоненциальное сглаживание.

**Проблема 2 — метрика не значит того, что написано.** Вычитается только `ACK_RANDOM_DELAY_AVG_MS = 45`, но не время в эфире heartbeat (~130 мс) и ACK (~119 мс). А `one_way = rtt / 2` README предлагает использовать для оценки расстояния — при том, что задержка распространения радиоволны на километр составляет **3.3 микросекунды**. Измеряется исключительно ToA, то есть константа при фиксированных RF-настройках.

**Фикс:**

```cpp
// server: в heartbeat
doc["seq"] = ++hbSeq;
// запоминать hbSentMs[seq % 4]

// client: эхом в ACK
doc["hb"] = lastHeartbeatSeq;

// server: считать RTT только при совпадении seq, иначе rtt = 0
```

И в UI переименовать поле — «отклик», не «расстояние». Соответствующий раздел README поправить.

### S6 — UI переключает вкладки под руками

**Где:** `server/data/index.html`, `loadStatus()`

```js
if (d.time_source === 'ntp')      { ...; switchClockTab('ntp'); }
else if (d.time_source === 'rtc') { ...; switchClockTab('rtc'); }
else                              { ...; switchClockTab('manual'); }
```

`loadStatus()` вызывается из `refreshAll()` каждые 5 секунд. Открыли вкладку Manual, начали вводить время — через 5 секунд интерфейс выкинул на RTC или NTP.

Рядом — вторая проблема: `refreshAll()` делает `Promise.all` из пяти параллельных `fetch`. ESP32-шный `WebServer` синхронный и обрабатывает **один** запрос за вызов `handleClient()`, то есть один за итерацию `loop()`. Часть запросов встаёт в очередь TCP-соединений и отваливается по таймауту, особенно на фоне C4.

**Фикс:** `switchClockTab()` вызывать только при первой загрузке и при явном действии пользователя. Пять запросов свести в один агрегирующий `GET /api/state`, интервал поллинга поднять до 10 с.

**Гигиена репозитория:** `.DS_Store` (в `data/`, заливается в SPIFFS), `fail.txt`, `need_run.txt` — удалить. `server/IMPORTANT` содержит полезные заметки по железу, но лежит без расширения в корне `server/` и содержит синтаксическую ошибку `radio.setBandwidth(LORA_BW / 1000.0;);` и устаревшую распиновку `DIO0 = GPIO26` — перенести в `docs/hardware-notes.md`, код поправить или убрать.

**Железо:** README рисует `SD → 3.3V` для MAX98357A, а `server/IMPORTANT` объясняет, что для моно-микса пин надо оставить в воздухе. Прямое подключение к 3.3V на большинстве плат выбирает только левый канал. Зависит от конкретного breakout — проверить и зафиксировать один вариант в README.

**Логика курса:** после дня 11 переход не предусмотрен — ни на 00, ни в состояние «курс окончен». Если это осознанно, стоит написать в README. Плюс auto-advance срабатывает только если устройство включено ровно в 00:00 — при ночном отключении питания день не сменится.
