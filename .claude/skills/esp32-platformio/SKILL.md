# ESP32 + PlatformIO Developer

Skill для полного цикла разработки на ESP32 с использованием PlatformIO: написание кода, отладка, объяснение концепций и связанные вопросы электроники.

## Как работать с этим skill

1. Определи тип задачи пользователя: **новый код**, **отладка/исправление ошибки**, **объяснение концепции**, или **вопрос по железу**. Часто это смесь — не ограничивайся одной категорией.
2. Прочитай соответствующий(е) reference-файл(ы) ниже перед тем как писать код или давать развёрнутый ответ.
3. Всегда уточняй конкретную плату (ESP32, ESP32-S2, ESP32-S3, ESP32-C3, ESP32-C6 и т.д.), если это влияет на ответ (разное число пинов, разные периферийные блоки, наличие USB-OTG и т.д.) — но не блокируй ответ вопросом, если можно дать разумный дефолт (обычный ESP32-WROOM-32) с оговоркой.

## Структура проекта PlatformIO (дефолт)

```
project/
├── platformio.ini       # конфигурация: платформа, плата, framework, либы, флаги
├── src/
│   └── main.cpp          # точка входа (setup() / loop())
├── include/               # заголовочные файлы проекта
├── lib/                   # приватные библиотеки проекта
├── test/                  # unit-тесты (Unity framework)
└── partitions.csv         # (опционально) кастомная разметка флеша
```

Минимальный `platformio.ini` для обычного ESP32:

```ini
[env:esp32dev]
platform = espressif32
board = esp32dev
framework = arduino
monitor_speed = 115200
```

Для ESP32-S3 / C3 меняется только `board` (например `esp32-s3-devkitc-1`, `esp32-c3-devkitm-1`) — проверяй актуальное имя платы в `pio boards espressif32` при сомнении, платы часто переименовываются.

## Reference-файлы — читай по необходимости

- **`references/peripherals.md`** — GPIO, ADC, PWM (LEDC), I2C, SPI, UART: как подключать, типовые пины, ловушки (ADC2 vs Wi-Fi, strapping pins и т.д.)
- **`references/freertos.md`** — задачи (tasks), очереди, семафоры, mutex, работа с двумя ядрами, типичные ошибки многозадачности
- **`references/connectivity.md`** — Wi-Fi (STA/AP/веб-сервер), BLE, MQTT, OTA-обновления
- **`references/power_and_sleep.md`** — режимы energy saving (light/deep sleep), пробуждение по таймеру/GPIO/тачу, измерение потребления
- **`references/debugging.md`** — типичные ошибки загрузки/подключения, работа с `pio device monitor`, чтение бэктрейсов (decode crash), JTAG-отладка
- **`references/hardware.md`** — электроника вокруг ESP32: питание (3.3V, просадки при Wi-Fi TX), подтяжки, развязка, типовые обвязки датчиков, ESD/EMC

Читай только то, что реально нужно для текущего вопроса — не подгружай всё сразу.

## Общие принципы при написании кода

- Пиши код с явной обработкой ошибок (проверяй возвращаемые значения `Wire.begin()`, `WiFi.status()`, коды ошибок SPIFFS/LittleFS и т.д.) — не оставляй "и так сойдёт" код, если пользователь не просил явно упрощённый пример.
- Указывай, какие пины **нельзя** свободно использовать на конкретной плате (strapping pins: GPIO0, GPIO2, GPIO12, GPIO15 на классическом ESP32; input-only пины GPIO34–39) — см. `references/peripherals.md`.
- Если код использует Wi-Fi/BLE — предупреждай о совместном использовании с ADC2 и о просадках по питанию при TX-импульсах (см. `references/hardware.md` и `references/power_and_sleep.md`).
- Для многозадачного кода на FreeRTOS всегда указывай размер стека и приоритет задачи явно, объясняя выбор — не оставляй "магические числа" без комментария.
- Когда пользователь просит объяснить концепцию — сначала дай короткую суть (2-3 предложения), потом при необходимости углубляйся; не превращай простой вопрос в лекцию, если не просили.

## Когда нужна электроника, а не только код

Если вопрос касается физического подключения (просадки питания, шумы на линии, неправильные показания датчика, платы, которые "виснут" при подключении определённой периферии) — это часто аппаратная проблема, а не программная. Проверяй `references/hardware.md` и явно разделяй в ответе: "это может быть проблема кода" vs "это похоже на аппаратную проблему" — вместо того чтобы предполагать одно по умолчанию.
