# Dynamic Course Editor — окончательная спецификация

Статус: утверждена заказчиком как архитектурная основа.
Дата: 2026-11-22.
Ветка: standalone-max.
Режим: READ ONLY до отдельного разрешения на реализацию.

Документ заменяет предыдущие архитектурные предложения. Исходный код прошивки не изменялся.

## 1. Назначение

Заменить фиксированный 13-дневный курс на циклический планировщик с курсами произвольной длины, редактором в Web GUI, независимым черновиком и атомарным применением конфигурации.

Главные инварианты:

- Курс — последовательность N календарных слотов, 1 <= N <= 47.
- После ручной активации курс привязан к календарной дате и повторяется бесконечно.
- День вычисляется по формуле, а не хранится и не увеличивается ежедневно.
- Действующий курс и черновик независимы.
- Apply не запускает звонки. Звонки начинаются только после Activate this day.
- Уже прошедшие события не воспроизводятся задним числом.
- При недостоверном времени звонки не выполняются.
- Ошибка не должна оставлять устройство в противоречивом состоянии.

## 2. Термины и состояния

- APPLIED — конфигурация опубликована, календарная привязка отсутствует, звонки запрещены.
- RUNNING — есть календарная привязка, звонки разрешены.
- SUSPENDED — обнаружена ошибка или недостоверное время, звонки запрещены, старый курс не возобновляется.
- EMERGENCY — после трёх неудачных восстановлений работает встроенное аварийное расписание.

Состояний Stop, Completed, Non-Stop и отдельного режима Service нет. Service — обычные календарные дни пересменки.

## 3. Модель курса и JSON v2

Курс:

- name — человекочитаемое имя.
- generation — целое число, увеличивается при каждой публикации.
- course_length — число дней N.
- templates — необязательный набор именованных списков событий.
- days — массив длины N. Каждый элемент содержит либо ссылку на шаблон, либо собственный список events.

Событие сохраняет текущие поля: id, hour, min, track, loop, vol, en, desc. Ограничения: не более 32 событий в дне, track 1..99, loop 1..7, vol 0..30, desc не длиннее DESC_MAX_BYTES.

Правила:

- День 13 эталонного курса создаётся как копия дня 12. После создания дни 12 и 13 редактируются независимо.
- Редактирование дня, который ссылается на общий шаблон, по умолчанию создаёт независимую копию событий для этого дня (copy-on-write). Редактирование самого шаблона — отдельная операция.
- Вставка дня: до или после выбранного, пустая или копия существующего.
- Удаление дня: вместе с событиями, с перенумерацией. Последний день удалить нельзя. День 0 удалить можно.
- Очистка дня: удалить все события, но оставить календарный слот.
- Merge Days отсутствует. Автоматического переноса событий между днями нет.

Формат v2:

    {
      "format": "gong-course",
      "version": 2,
      "name": "...",
      "generation": 1,
      "course_length": 14,
      "templates": {
        "arrival": [ ... ],
        "practice1": [ ... ],
        "departure": [ ... ],
        "service": [ ... ]
      },
      "days": [
        { "template": "arrival" },
        { "template": "practice1" },
        ...
        { "events": [ ... ] }
      ]
    }

Экспорт всегда отдаёт v2. Импорт принимает v1 и v2. v1 с полями templates и days, где день может быть именем шаблона или встроенным массивом событий, преобразуется в v2 без потери событий. Ошибка импорта не меняет действующий курс.

## 4. Хранение и атомарность

LittleFS:

- Действующий курс хранится в каталоге поколения: /course/g<gen>/meta.json и /course/g<gen>/dNN.json.
- Структура поколения неизменяема: meta.json, число дней и generation не меняются после публикации. Файлы отдельных дней могут атомарно заменяться при обычном редактировании событий.
- meta.json записывается последним и содержит generation, course_length, имя и контрольную сумму структуры. Хеши отдельных дней в мету не входят, чтобы обычная правка события не требовала переписывать мету.
- Активное поколение выбирается одной записью NVS. Структурные изменения (вставка, удаление, замена курса, импорт) создают новое поколение. Обычная правка события заменяет только файл соответствующего дня.
- Черновик хранится отдельным поколением. После Apply черновик может ссылаться на то же поколение; при первом структурном редактировании создаётся новое поколение черновика (copy-on-write).
- Apply: собрать новое поколение во временном каталоге, проверить все дни, записать meta.json, затем одной записью NVS переключить active_generation. Старое поколение удаляется только после успешной публикации и успешной загрузки активного дня.
- Обрыв питания до NVS-фиксации оставляет старый курс. Обрыв после фиксации оставляет новый целый курс. Смеси старого и нового нет.
- Последовательное переименование dayNN.conf из текущего sched_commitCourse() не используется: оно допускает смесь дней при обрыве.

NVS:

- Один ключ course_state: schema, active_generation, draft_generation, day_index, activation_date, course_length, flags, failure_count, CRC.
- Отдельный ключ last_fire: generation, day_index, minute, event_id, date, timestamp, CRC.
- Отдельный ключ emg_last_fire для аварийного расписания.
- course_state пишется при Apply, Activate, ошибке, входе и выходе из аварии. В полночь course_state не пишется.
- last_fire пишется при каждом отзвонившем событии. Это несколько записей в сутки, не ежедневная запись календаря.
- last_fire намеренно отделён от course_state: иначе каждый звонок перезаписывал бы календарную привязку, рос бы износ NVS и любая ошибка записи затрагивала бы и календарь, и защиту от повторов. Разделение изолирует сбои: повреждённый last_fire приводит максимум к одному возможному повтору, повреждённый course_state — к SUSPENDED без звонков.
- Если last_fire не соответствует generation/day_index из course_state, он считается устаревшим и игнорируется.

## 4A. Обычное редактирование событий и структурные изменения

Существуют два разных типа редактирования. Их нельзя смешивать.

A. Обычное редактирование событий.

- Оператор может включать и выключать события, добавлять и удалять события, менять название, описание, время, громкость, loop и track.
- Изменения применяются сразу и не требуют Activate this day.
- Календарная привязка и текущий день не меняются.
- Если изменён текущий день, массив событий в RAM обновляется сразу. Планировщик начинает использовать новые события без перезагрузки.
- Если изменён будущий день, RAM не меняется. Новый файл дня будет загружен при наступлении этого дня.
- Уже прошедшие события не воспроизводятся задним числом.
- Обычное редактирование не прерывает текущий MP3. Если звук играет, запись на LittleFS откладывается, а RAM обновляется сразу. Отложенная запись выполняется, когда звук закончится, и до перехода через полночь.
- Для обычного редактирования не нужна кнопка Apply и не создаётся новое поколение курса.
- Существующие API и поведение Web GUI сохраняются: GET /api/day?n=N, POST/PUT/DELETE /api/day/entry. Внутренняя реализация сохранения меняется на атомарную замену файла дня.

Атомарная замена файла дня:

1. Сформировать новый JSON дня в RAM.
2. Записать его во временный файл /course/g<gen>/dNN.tmp.
3. Закрыть файл, проверить размер и разбор JSON.
4. Переименовать dNN.tmp в dNN.json. Если целевой файл уже существует и rename не заменяет его, использовать резервную копию dNN.bak и восстановление при загрузке.
5. При обрыве питания допускается только целый старый или целый новый файл. Частично записанный dNN.json не должен оставаться.
6. При загрузке временные и резервные файлы сверяются: если dNN.json отсутствует, восстанавливается dNN.bak; если dNN.json цел, dNN.tmp удаляется.
7. meta.json и generation при обычной правке не меняются.

Ограничение: если правка сделана во время звука и питание пропало до отложенной записи, эта правка теряется. Это сохраняет текущее поведение и не прерывает звук. Потерянный файл не повреждает старый: на диске остаётся целая предыдущая версия дня.

### 4A.1. Совместимость с существующим редактором

Требование заказчика: сохранить существующее поведение редактора событий. Проверенная реализация:

- Маршруты и поля уже существуют: `GET /api/day?n=N`, `POST/PUT/DELETE /api/day/entry`, `GET /api/days` (`webhandler.cpp:523-570, 737-743`). Web GUI использует именно их (`server/web/index.html:730-745, 913-920`).
- Для активного дня `sched_addToDay()`, `sched_editInDay()`, `sched_delFromDay()` делегируют в `sched_add()`, `sched_edit()`, `sched_del()` (`schedule.cpp:780-868`). Те сначала меняют `entries[]` в RAM, затем вызывают `sched_save()`.
- `sched_save()` при играющем MP3 не пишет файл, а ставит `schedPendingSave`; RAM уже содержит новое событие, поэтому API и GUI видят изменение сразу. Запись выполняется из `sched_check()` после окончания звука (`schedule.cpp:521-534, 341-346`).
- Для неактивного дня правка читает `/dayNN.conf`, меняет JSON и сразу пишет файл (`schedule.cpp:766-778`). Это поведение сохраняется, но запись заменяется на атомарную по разделу выше.
- Текущий `saveDayArray()` открывает целевой файл на `"w"` (`schedule.cpp:773`), поэтому обрыв питания во время записи может оставить частичный JSON. Это подтверждённый дефект, который устраняет атомарная замена.
- Обычная правка активного дня не должна менять generation, meta.json и календарную привязку. Структурные операции по-прежнему идут только через черновик и Apply.

Итог: API, имена полей и поведение «изменение видно сразу, звук не прерывается» сохраняются. Меняется только внутренний способ записи файла дня и добавляется явное разделение A/B.

B. Структурное изменение курса.

- Вставка и удаление календарных дней, изменение количества дней, замена курса целиком, импорт новой конфигурации.
- Выполняется только в независимом черновике.
- Для применения нужен отдельный Apply с подтверждением.
- Apply создаёт новое поколение, проверяет все дни, записывает meta.json и одной записью NVS переключает active_generation.
- После структурного Apply календарная привязка сбрасывается, состояние APPLIED, звонки не выполняются до Activate this day.
- Структурное изменение не должно менять действующий курс до Apply.

## 5. Формула дня

При активации сохраняются:

- activated_day — индекс выбранного дня;
- activation_date — гражданская дата YYYYMMDD;
- course_length — N.

Текущий день:

    day = (activated_day + civil_days_between(activation_date, today)) % course_length

civil_days_between считает разницу по гражданским датам, без деления time_t на 86400 и без DST. Текущий daysBetween() (schedule.cpp:93-104) для новой модели не используется.

Пример: активация 22.11.2026 дня 5 при длине 14. 23.11 — день 6, 05.12 — день 4, 06.12 — день 5.

## 6. Ручная активация

Порядок:

1. Немедленно остановить MP3 и loop, сбросить повторы. Используется существующий mp3_stop(), который очищает loopRemain (mp3handler.cpp:139-145).
2. Записать в NVS course_state со flags=SUSPENDED и новым generation/днём/датой, но без публикации звука. Это гарантирует, что после сбоя старый курс не возобновится.
3. Прочитать и проверить весь курс по одному дню, без загрузки всех 47 дней в RAM. Проверить выбранный день и meta.json.
4. При успехе записать course_state со flags=RUNNING, опубликовать события выбранного дня в RAM, сбросить failure_count, включить планировщик.
5. При ошибке оставить SUSPENDED, записать причину в журнал, показать ошибку в GUI, перезагрузить через 10 секунд. Старый курс не возобновлять.

Активировать можно любой день. Уже прошедшие события этого дня не воспроизводятся. Повторная активация того же дня на ту же дату не должна повторять уже отзвонившие события: last_fire сохраняется.

## 7. Автоматический переход через полночь

- Если звук не играет: вычислить фактический день по формуле, загрузить его расписание, продолжить.
- Если звук играет: не прерывать. Дождаться окончания трека и всех повторов. После окончания вычислить фактический день. Если дата уже ушла вперёд, загрузить фактический текущий день. События с временем раньше момента переключения не играть.
- В полночь NVS не писать. Привязка не меняется.
- Ошибка загрузки: остановить звонки, записать причину, перезагрузить. Предыдущий день не продолжать.
- sched_catchup() в новой модели отключается: он воспроизводит пропущенное событие в пределах 120 секунд после перезагрузки (schedule.cpp:295-315), что противоречит запрету играть задним числом.

## 8. Защита от повторного звонка

Порядок с учётом существующего lastfire и отказов питания:

1. При загрузке прочитать last_fire. Если CRC неверна, считать запись отсутствующей и записать диагностику.
2. В sched_check() перед звонком:
   - если now < last_fire.timestamp, считать, что часы переведены назад. Не играть события, записать предупреждение, показать в GUI. Оператор может выполнить Activate для новой привязки. Это предотвращает повтор уже отзвонивших событий.
   - если generation + day_index + minute + event_id + date совпадают с last_fire, событие уже отзвонило, пропустить.
   - если lastFiredKey совпадает и с момента звонка прошло менее 65 секунд, пропустить (существующая RAM-защита).
3. Порядок звонка: сначала вызвать onScheduleTrigger (звук), затем обновить last_fire в RAM и записать его в NVS. Проверить результат записи. Если запись не удалась, записать ошибку в журнал, но не повторять звук. Это сохраняет приоритет «не пропустить звонок»; возможен редкий повтор только если питание пропало между началом звука и записью last_fire.
4. При автоматическом переходе через полночь day_index меняется, поэтому last_fire прошлого дня не блокирует события нового дня.
5. При ручной активации другого дня или другой даты last_fire не совпадает по идентичности и не мешает новым событиям. При активации того же дня и той же даты last_fire сохраняется и защищает от повтора.
6. Аварийное расписание использует отдельный emg_last_fire, чтобы не влиять на обычный курс.

Новая подсистема не создаётся: расширяется существующая логика lastFiredKey/lastFireTs и ключ lastfire. Конкретный дефект текущего кода: doFire() вызывает звук до записи lastfire и игнорирует результат putUInt (schedule.cpp:273-284); lastFireTs хранит только время, поэтому после перезагрузки и перевода часов назад возможен повтор. Минимальное исправление — идентичность события и проверка записи, как выше.

## 9. Аварийное расписание и восстановление

Аварийное исполнение и проверка восстановления разделены.

Аварийное исполнение:

- Встроенная таблица в прошивке, не зависит от LittleFS и пользовательского JSON.
- 04:00 — стандартный гонг, трек 1, 1 воспроизведение, громкость 30.
- 04:20 — то же.
- 06:30 — то же.
- 06:31 — трек 1, ровно 10 воспроизведений, громкость 5 из 30.
- mp3_play(track, loops) трактует второй аргумент как общее число воспроизведений: loopRemain = loops - 1 (mp3handler.cpp:124-130). Поэтому для 10 воспроизведений передаётся 10, а не 11. Глобальный LOOP_MAX не меняется.
- Аварийный исполнитель вызывается каждую секунду, не читает файлы, не перезагружает устройство при ошибке звука или NVS. Использует emg_last_fire для защиты от повтора.

Проверка восстановления:

- Отдельный периодический вызов (например, раз в 5 минут) и ручной вызов из GUI.
- Проверяет course_state, meta.json активного поколения и файл текущего дня. Полная проверка всех дней — при ручном retry.
- При успехе: снять EMERGENCY, записать RUNNING, сбросить failure_count, опубликовать текущий день, включить обычный планировщик.
- При неудаче: остаться в EMERGENCY, записать причину, не перезагружаться.
- В EMERGENCY загрузка не пытается запустить обычный курс и не перезагружается. Это исключает бесконечный цикл.
- Ручная активация в EMERGENCY при ошибке не перезагружает устройство, а возвращает ошибку в GUI.

Счётчик неудач:

- failure_count хранится в NVS и переживает перезагрузку.
- Увеличивается при ошибке загрузки в RUNNING, при ошибке ручной активации и при ошибке автоматического перехода.
- После третьей неудачи включается EMERGENCY.
- Сбрасывается при успешной активации, успешном переходе и успешном восстановлении.

## 10. RAM и производительность

- В RAM только события активного дня, до 32 записей.
- JSON-пул до 12 КБ, размер по файлу (dayPoolSize).
- Apply и Activate проверяют дни по одному, без массива всех 47 дней.
- Экспорт потоковый, без reserve(DAY_COUNT * 2048).
- Импорт потоковый, без одновременной загрузки всего курса.
- Долгие операции с LittleFS выполняются вне sys_lock. Публикация в RAM — под коротким sys_lock.
- Web-сервер не должен одновременно отдавать большой ответ и выполнять Apply/Activate. Используется отдельный course operation lock.
- Watchdog: циклы проверки 47 дней должны регулярно отдавать управление.

## 11. Web GUI и API

Маршруты (все изменяющие требуют существующей авторизации R_WRITE, чтение — R_AUTH):

- GET /api/course — метаданные, состояние, активный день, длина, ошибка.
- GET /api/course/day?i=N — события дня черновика.
- PUT /api/course/day?i=N — сохранить события дня черновика.
- POST /api/course/insert?i=N&mode=empty|copy — вставить день до N.
- DELETE /api/course/day?i=N — удалить день, кроме последнего.
- POST /api/course/clear?i=N — очистить события дня, оставить слот.
- GET/PUT /api/course/template?name=... — чтение и правка шаблона.
- POST /api/course/apply — полная проверка и атомарная публикация.
- POST /api/course/activate?i=N — ручная активация.
- GET /api/course/export — экспорт v2.
- POST /api/course/import — импорт v1/v2.
- GET /api/course/status — состояние, failure_count, причина аварии.
- POST /api/course/emergency/retry — ручная проверка восстановления.

Сохраняются существующие маршруты обычного редактирования событий:

- GET /api/day?n=N — чтение дня.
- POST /api/day/entry — добавление события.
- PUT /api/day/entry — изменение события.
- DELETE /api/day/entry — удаление события.
- GET /api/days — список дней и их состояние.

GUI:

- Экран действующего курса: состояние, активный день, дата активации, длина, кнопка Activate.
- Редактор событий действующего курса: обычные правки применяются сразу, без Activate и без Apply. Сохраняются существующие поля и поведение редактора.
- Экран черновика: структурные изменения — вставка, удаление, замена, импорт, затем отдельный Apply.
- Ошибки и авария показываются явно, с причиной и кнопкой повторной проверки.
- Структурные изменения действующего курса идут только через черновик. Обычные правки событий действующего курса разрешены напрямую и не меняют календарную привязку.

## 12. Первый запуск и совместимость

- Миграции старых 13 дней нет. Заказчик очищает NVS и LittleFS перед прошивкой.
- На чистом устройстве создаётся поколение 1 с 14-дневным эталоном: день 0 — заезд, дни 1-10 — практика, день 11 — отъезд, день 12 — Service, день 13 — копия дня 12.
- Состояние APPLIED, звонки запрещены, ожидается Activate.
- Старые ключи NVS и старые dayNN.conf не читаются новым планировщиком. Код active_day_state остаётся в дереве как исторический, но не используется новым путём.
- Импорт v1 поддерживается только как файл, не как миграция устройства.

## 13. Ограничения и риски

- Поведение LittleFS/NVS при обрыве питания на реальном ESP32 не проверено. Проверка только на стенде и в host-тестах.
- Точность DS3231 за 47 дней и поведение SNTP при скачках времени не проверены.
- Реальный пик heap при фрагментированной памяти не измерен.
- Аварийное расписание и громкость 5/30 требуют проверки на железе.
- Доступность MP3-треков и фактическое звучание после сбоя не проверены.

## 14. Что не входит в спецификацию

- Миграция старых курсов.
- Отдельный режим Stop/Completed/Non-Stop.
- Merge Days.
- Изменение GPIO, audio, LoRa, WiFi, config.h.
- Прошивка устройства и стирание NVS/LittleFS без отдельного разрешения.
