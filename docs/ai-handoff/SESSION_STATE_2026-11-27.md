# Сессия 2026-11-27: ветка `standalone-max-button` (кнопка + LED)

Ветка: `standalone-max-button` (новая, отдельный worktree
`/root/gong-standalone-max-button`), база — `standalone-max` `c5cc32e`.
`standalone-max` и `standalone` не менялись.

## Задача

Вернуть на актуальную архитектуру физическую кнопку и светодиод состояния,
удалённые в `b050f42` (LED + реле) и `b9d3aaa` (кнопка), не откатывая
CourseStore, course_editor, active_day_state, emergency и не возвращая
`relayhandler`.

## Инварианты, которые нельзя ломать

1. `BUTTON_PIN` и `STATUS_LED_PIN` по умолчанию **-1**. Включение — только после
   подтверждения физической платы (см. ниже), вместе с `build_flags`.
2. Кнопка не вызывает `mp3_*`/`sched_*`/`web_*` напрямую — только через
   `ButtonHooks` из `main.cpp`. Иначе host-тесты перестанут компилироваться.
3. Ручной запуск идёт только через `mp3_manualPlay()`: `/api/play` и кнопка
   обязаны иметь одинаковые правила.
4. `web_resetAuth()` стирает только `auth` (+ `/auth.conf`). Никаких
   `nvs_flash_erase`, `LittleFS.format`, удаления курсов.
5. `led_loop()`/`button_loop()` остаются внутри `sys_lock()` в `controlTask`;
   порядок `sys_lock -> audioMtx/logMtx` не меняется.
6. Новый `.cpp` в `server/src` не линкуется в host-раннеры автоматически — для
   кнопки добавлен отдельный раннер, прежние не тронуты.

## Блокирующий аппаратный вопрос

`server/platformio.ini`: `board = esp32-s3-devkitc-1`, а физическая плата —
ESP32-D0WD-V3 (классический ESP32), на которой и снята схема
(`footprint/schematic_netlist.md`: GPIO32 = BUTTON, GPIO13 = STATUS_LED). Номера
GPIO32/13 есть у обоих чипов, но двоичная прошивка S3 на классическом ESP32 не
запустится. Пока плата не подтверждена:

- кнопка/LED выключены (`-1`), прошивка собирается как раньше;
- `GONG_GPIO_VALID()` в `config.h` даёт `#error` только на несуществующие у
  целевого чипа номера (S3: 22–25; ESP32: 40–48);
- включённый код проверен только компиляцией целевым тулчейном:
  `PLATFORMIO_BUILD_FLAGS="-DBUTTON_PIN=32 -DSTATUS_LED_PIN=13" pio run -e esp32dev`
  (SUCCESS; binary для S3, на плату не прошивается).

## Итоги независимого review (openai/gpt-6.2-astra)

Ревьюер нашёл 11 замечаний; приняты и исправлены (с регрессионными host-тестами):

1. Вход читался до `pinMode()` — теперь `button_bootProbe()` настраивает вывод
   до первого `digitalRead()`.
2. Сброс мог выдаться после отпускания раньше порога — порог считается только
   пока СЫРОЙ уровень «нажато»; отпускание отменяет сброс.
3. 10 с считались от конца инициализации — отсчёт от подачи питания (`probe`
   первой строкой `setup()`); нажатие, начавшееся позже, за зажатое не считается.
4. Стоп терялся на границе 1000 мс, а залипание — на 60000 мс — оба граничных
   случая решены при отпускании по измеренной длительности.
5. Конец трека в первые 50 мс дребезга превращал стоп в гонг — решение «стоп или
   действие» снимается на сыром фронте нажатия.
6. Сброс сообщал об успехе при неудалённом `/auth.conf`/отказе NVS — теперь
   `web_resetAuth()` возвращает `bool`, неудаление файла считается ошибкой.
7. Кнопка расходилась с `/api/play` при отсутствии файла трека — лишняя проверка
   `mp3_trackExists()` убрана, путь один.
8. Аллокация/блокирующее I/O в обработчике кнопки — убрана вместе с п.7; остался
   только `audioMtx` (`portMAX_DELAY`), как и в штатном `/api/play` под `sys_lock`
   (риск зафиксирован, не закрыт).
9. LED-фаза переполнялась через 49.7 суток — фаза хранится как остаток по модулю
   периода, накопитель не может переполниться.
10. `esp_task_wdt_reset()` до подписки задачи — кормление только при
    `esp_task_wdt_status(nullptr) == ESP_OK`.
11. Проверка GPIO отбрасывала существующие выводы S3 — `GONG_GPIO_VALID()`
    повторяет маску чипа (S3: 0–21, 26–48; ESP32: 0–39).

Отклонено как неверное фактическое утверждение: «на ESP32-S3 нет GPIO32».
У S3 существуют 0–21 и 26–48, поэтому GPIO32 есть; блокер — не номер вывода, а
несовпадение `board` с физической платой. Формулировки в `config.h` и docs
исправлены.

Принято как открытый риск (не дефект): блокировка `audioMtx` внутри `sys_lock`
на пути ручного запуска; задержка ограничена длительностью одного
`audio.loop()`, но на стенде не измерялась.

## Дополнение: реле внешнего усилителя

По решению владельца ограничение «реле не восстанавливать» отменено. Добавлен
`server/src/relayhandler.{h,cpp}` и интеграция; спецификация — `docs/RELAY.md`.

Ключевые решения (ответы владельца Q1–Q7):

- реле коммутирует внешний усилитель; MAX98357A питается независимо,
  `Always OFF` не глушит встроенный гонг;
- при загрузке реле OFF, сохранённый `Always ON` не восстанавливается;
- полярность не подтверждена — поддержаны оба уровня, `RELAY_PIN = -1` по
  умолчанию;
- кнопка: 3–8 с гонг, ≥ 8 с переключение реле; при звуке/прогреве только STOP;
- восстановлены режимы AUTO/ON/OFF, warm-up 800 мс, hold 3000 мс, ручные 30 мин,
  LED-подсказка 2 Гц, предвключение, отмена pending, единый путь звука.

Интеграция: `mp3_manualPlay → relay_play`, `onGongFire → relay_play`,
`relay_stop` вместо `mp3_stop` в `schedule.cpp` (в т.ч. `courseActivate` и
`sched_courseApply`), `sched_msToNext()` для предвключения (учитывает курс,
день, отмену событий, время, emergency), `relay_loop` в `controlTask`, `/api/relay`
и карточка Gong & Relay.

Проверки: relay 103 + 17 (disabled), button 532, scheduler 270, остальные без
изменений; ASan/UBSan чисто; сборка SUCCESS (RAM 21.0 %, Flash 88.0 %;
включённая конфигурация — 21.2 % / 88.9 %).
