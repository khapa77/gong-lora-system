## 5. Предварительный технический план (не утверждён)

Версия плана до ревью Astra. Исправления по ревью — в разделе 6; они имеют приоритет.

**Модель курса**

- Тип `course` (N дней практики, 1–45) или `service`.
- Пять шаблонов по 32 события в нынешнем формате записи: `hour, min, track, loop, vol, en, desc`.
- Для дней 1..N хранится, какой из вариантов 1/2/3 звонит в этот день.
- `DAY_COUNT` в новом коде не используется; остаётся как длина старого курса для миграции. `config.h` не меняется.

**Хранение на LittleFS**

- Шаблоны в двух слотах: `/ta0.conf`–`/ta4.conf` и `/tb0.conf`–`/tb4.conf`.
- Черновик пишется в недействующий слот.
- Старые `/dayNN.conf` и `/gong.conf` не удаляются и не переписываются.
- Оценка места: около 50 КБ полезных данных (Astra: это не верхняя граница).

**Состояние в NVS**

- Один новый ключ `gong/course` (u64) без отдельного маркера, чтобы не повторять B1.
- Хранится дата старта курса, а не пара «день + дата». Текущий день = сегодня минус дата старта.
- NVS пишется при Start, Stop, Save, а не каждую полночь.
- Старые ключи `active`, `active_schema`, `aday`, `adate` не трогаются.

**Память**

- В RAM только шаблон текущего дня: существующий массив на 32 записи плюс временный JSON-пул до 12 КБ при загрузке.
- Экспорт собирает браузер из метаданных и пяти запросов шаблонов. Нынешний экспорт резервирует `DAY_COUNT × 2048` байт одним блоком (`schedule.cpp:977`), при 47 днях это 96 КБ.

**Планировщик**

- При смене дня шаблон только читается.
- Пока смена дня отложена из-за звука, гонги по старому дню не проверяются.
- Неудачная загрузка шаблона — Error с флагом в GUI, повтор не чаще раза в минуту.
- Результат записи `lastfire` проверяется.

**Формат JSON v2 (предварительно)**

```json
{
  "format": "gong-course",
  "version": 2,
  "name": "...",
  "type": "course",
  "practice_days": 10,
  "templates": {
    "arrival": [], "variant1": [], "variant2": [], "variant3": [], "departure": []
  },
  "variants": "1111111111"
}
```

Для Service в экспорт нужно добавить выбранный шаблон (замечание Astra).

**Формат v1 (существующий)**

```json
{
  "format": "gong-course",
  "version": 1,
  "name": "...",
  "templates": { "имя": [ ... ] },
  "days": ["имя", "имя", ...]
}
```

В `days` ровно 13 элементов; элемент может быть именем шаблона или списком событий целиком. Импорт v1 должен читать обе формы. Преобразование: первый день — заезд, последний — отъезд, различающиеся дни между ними — варианты 1–3; больше трёх разных дней практики — отказ с объяснением.

**Миграция при первой загрузке (предварительно)**

1. Если нового курса нет, прочитать старое состояние и `/dayNN.conf`.
2. Построить шаблоны из старых файлов. Времена звонков берутся только оттуда.
3. Если преобразование без потерь и старое состояние валидно, курс продолжается.
4. Иначе Error с объяснением; старые файлы целы.

**API (предварительно)**

- Новые: `GET /api/course`, `GET /api/course/template`, `POST /api/course/edit|cancel|save|start|stop`, `POST /api/course/day`, `/api/course/draft/meta|entry|clear|template`.
- Старые `/api/day*`, `/api/course/day`, `/api/course/commit` заменяются.

## 6. Ревью архитектуры Astra: «нужны изменения до утверждения»

Astra одобрила дату старта, пять шаблонов и загрузку только активного шаблона. Обязательные изменения:

1. **Одна точка фиксации.** Метаданные хранить внутри каждого слота, записывать последними. Действующий слот, состояние, поколение и дату старта выбирает одна запись NVS. Отдельного `/course.json` нет. Иначе обрыв при первой миграции даёт Error без выхода.
2. **Completed фиксируется и сам не снимается.** Вычисляемый Completed нарушает требование 6: перевод часов назад сам возобновляет гонги. Неверная будущая дата RTC не должна необратимо завершать курс.
3. **Идентичность звонка.** `lastfire` хранит время вызова, защита в RAM живёт 65 секунд. Нужно хранить последнее отзвонившее событие (запуск курса, день, минута). Start и ручная коррекция дня не догоняют события, назначенные до команды.
4. **Миграция.**
   - Старое состояние «день известен, дата не привязана» законно, формула «дата минус день» для него не работает.
   - Пустое устройство не запускает курс само.
   - Дни сравнивать по полям событий, а не по байтам.
   - Нужен строгий валидатор: `prepareFromPath` молча обрезает день до 32 записей и подставляет 00:00 вместо отсутствующего времени (`schedule.cpp:548, 562-563`).
   - Откат на старую прошивку возможен, но не бесшовен.
5. **Редактор и API.**
   - У черновика номер сеанса и ревизия (защита от старой вкладки).
   - Каждая правка черновика заменяет файл атомарно; у импорта признак завершения.
   - Экспорт проверяет ревизию на каждом запросе.
   - Строгий разбор параметров: сейчас отсутствующий номер превращается в 0 (`webhandler.cpp:524, 544`), а 0 — шаблон заезда.
   - Долгие файловые операции не держат общий замок `sys_lock`: под ним работает планировщик, обе задачи под watchdog.
   - Не повторять `remove(to)` перед повторным `rename` (`schedule.cpp:952`).
   - Выход из Error: повторить чтение, скачать уцелевшее, создать или импортировать курс заново.
6. **Тесты.** Часть существующих host-тестов проверяет старый контракт; их оставить как тесты чтения старых данных. Добавить тесты обрыва на каждой границе Save, Start, Stop, входа в редактор и миграции, двух клиентов, потерянного ответа. Симуляция 47 суток эти тесты не заменяет.

Что из ревью проверено по строкам основным агентом: замечания про загрузчик, разбор параметров, общий замок, однократность `Store::load`, `remove` перед `rename`. Ссылки Astra на строки `index.html` и тестовых файлов не сверялись.

## 8. Известные дефекты B1–B5

- **B1.** Обрыв питания между записью маркера `active_schema` и `active` при первой записи навсегда оставляет `Unknown` (`active_day_state.cpp:154, 198-210`). Осознанный fail-closed, закреплён тестом. Суточных переключений не касается. Подтверждён Astra.
- **B2.** У `sched_recover`, `sched_load`, `sched_resume` нет вызывающих в `server/src` (`schedule.cpp:586, 686, 704`). Состояния Unknown и Blocked через UI не снимаются. При разовом сбое помогает перезагрузка, при B1 не помогает. Подтверждён Astra.
- **B3.** Перевод даты назад и обратно (или вперёд и обратно) сдвигает курс вперёд (`schedule.cpp:244-260`). Исправляется ручной активацией дня. Уточнён Astra.
- **B4.** Результат авто-переключения дня игнорируется (`schedule.cpp:260`). Если файл следующего дня не разбирается или не хватило памяти, звонит вчерашнее расписание, `sched_hasError()` ложно, попытка повторяется раз в секунду. При сбое NVS иначе: статус Unknown, ошибка видна. Уточнён Astra.
