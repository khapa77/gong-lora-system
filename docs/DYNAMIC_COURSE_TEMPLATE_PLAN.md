# План хранения курса через шаблоны (JSON v1: templates + days)

Статус: архитектура принята заказчиком; **этап A реализован**, этапы B–F не начаты.
Дата: 2026-11-23. Ветка: `standalone-max`. База: `dcb2603`.

## 1. Зачем

Операторский JSON v2 с полным перечислением событий каждого дня даёт большой файл и
заставляет хранилище разворачивать каждый день в отдельный файл: одинаковые расписания
копируются по числу календарных дней. На ESP32 без PSRAM это лишний объём LittleFS,
лишняя RAM на разбор и лишний износ флеша.

Измерено на host тем же кодом хранения:

| Вариант | файлов | LittleFS | макс. файл дня | RAM `loadDay` |
|---|---|---|---|---|
| `docs/course-example.json` (13 дн., 5 шаблонов, 50 уник. событий) | 14 | 21 466 Б | 1 876 Б | 38 КБ (15 событий) |
| операторский профиль 14 дн. (4 шаблона, 42 уник. события, 1 правленый день) | 15 | 14 505 Б | 1 149 Б | 29 КБ (12 событий) |
| тот же курс, уже развёрнутый | 15 | 14 510 Б | 1 149 Б | 29 КБ |
| предлагаемое компактное хранение того же 14-дневного | 16 | ≈6 078 Б | ≈900 Б | цель 1–2 КБ |

Ключевой вывод: материализация сегодня происходит **безусловно**
(`course_store.cpp:678` `toJsonV2(one, true)` внутри `saveDayAtomic`), поэтому шаблонный
и развёрнутый курс на флеше занимают одинаково.

## 2. Архитектура хранения (принята)

```
/course/g<N>/meta.json        — как сейчас; у шаблонных поколений добавляется "layout":"tpl1"
/course/g<N>/templates.json   — НОВЫЙ файл: {"format":"gong-course-templates","version":1,
                                 "templates":{"имя":[event...], ...}}   (та же CRC-обёртка)
/course/g<N>/dNN.json         — формат дня НЕ меняется:
                                 {"days":[{"template":"practice"}]}   ← ссылка
                                 {"days":[{"events":[...]}]}           ← собственные события дня
```

Инварианты:

- Старые опубликованные поколения (`layout` отсутствует = expanded) **не зависят** от
  `templates.json` и читаются ровно как раньше.
- Маркер `layout` пишется только новыми поколениями (этап B). Этап A только умеет его
  читать/писать через `CourseMeta`.
- Смешанное поколение допустимо: часть дней — ссылки, часть — с собственными событиями
  (правка дня материализует только этот день).
- Планировщик по-прежнему загружает только текущий день (`schedule.cpp:185`).

## 3. Этап A — объём работ (Course Store)

Только `server/src/course_store.{h,cpp}` и тесты. Импорт, публикация (Apply) и экспорт
**не меняются**; новых шаблонных поколений на устройстве этот этап не создаёт.

1. `templates.json`:
   - `writeTemplates(generation, map, error)` — атомарная запись (tmp → bak → rename,
     CRC, read-back), как для дней;
   - чтение с проверкой CRC и разбором **по одному шаблону** (пик — один шаблон,
     не весь файл).
2. `TemplateCache` (singleton, строго привязан к generation):
   - `prepareTemplates(generation, error)` — загружает один раз; при смене поколения
     старая запись инвалидируется **до** загрузки новой;
   - `templatesReady(generation)`, `invalidateTemplates()`, счётчики для диагностики;
   - любая ошибка загрузки оставляет кэш пустым (fail-closed).
3. `loadDay()`:
   - день с собственными событиями — как раньше;
   - день-ссылка — разрешается из кэша; нет кэша для этого generation или нет шаблона →
     **ошибка**, а не пустое/частичное расписание.
4. `validateGeneration()` — для `layout=tpl1` сначала готовит кэш, затем проверяет все дни.
5. `recover()` — восстанавливает `templates.json` тем же `recoverBase`, только для
   `layout=tpl1`.
6. `deleteGeneration()` — удаляет `templates.json` (+ `.tmp`/`.bak`) и инвалидирует кэш,
   если удаляется закэшированное поколение.
7. `cloneGeneration()` — копирует `templates.json`, если исходное поколение шаблонное.

Лимиты (проверяются при загрузке, ошибка — понятная строка):
`≤32` шаблона, `≤32` события в шаблоне (правило модели), `≤256` событий суммарно.
Пик RAM при загрузке ≈ один шаблон (12 событий ≈ 30 КБ, 32 события ≈ 84 КБ), резидентно ≈2 КБ.

## 4. Состояния после Apply/Activate (уточнение)

После Apply (в т.ч. первого) корректное состояние: `APPLIED`, `running=false`,
`activation_date=0`, `day_index=-1` (день не привязан, звонков нет). Прежнее ожидание
`day_index=0` в черновике плана было ошибочным — тесты этапов B–F должны проверять `-1`.
После ручной активации дня N: `RUNNING`, `day_index=N`, `activation_date=YYYYMMDD`.

## 5. Что НЕ входит в этап A

- Запись ссылочных дней при импорте/пресетах (этап B).
- Материализация дня при обычной правке (copy-on-write, этап C).
- Компактный экспорт (этап D).
- Загрузка кэша в загрузчике планировщика и при Apply/Activate (этап E).
- Миграция уже опубликованных курсов (не требуется; повторный импорт + Apply).

## 6. Регрессионные тесты этапа A

1. Старое развёрнутое поколение: мета без `layout`, `loadDay` работает без `templates.json`.
2. Шаблонное поколение: `writeTemplates` + мета `tpl1` + дни-ссылки → `loadDay` отдаёт
   ровно события шаблона.
3. Смешанное поколение: день-ссылка и день с собственными событиями в одном поколении,
   каждый даёт свои события.
4. Отсутствующий шаблон у дня-ссылки → ошибка `loadDay`, пустых расписаний нет.
5. Битый `templates.json` (мусор вместо JSON) → `prepareTemplates` = false, кэш пуст,
   `loadDay` ссылочного дня = false.
6. Ошибка CRC (валидный JSON, неверный заголовок) → то же.
7. Неверный generation кэша: после `prepare(A)` чтение ссылочного дня поколения B — ошибка;
   после `prepare(B)` — данные B, без «протечки» A.
8. Сбой загрузки инвалидирует кэш: успешный `prepare`, затем битый файл + `invalidate`/
   повторный `prepare` → кэш пуст, старые шаблоны не отдаются.
9. `recover()` восстанавливает `templates.json` из `.bak` и из `.tmp` после обрыва.
10. `deleteGeneration()` удаляет файл шаблонов и инвалидирует кэш.
11. Лимиты: 33 шаблона → ошибка; >256 событий суммарно → ошибка.
12. `validateGeneration()`: шаблонное поколение с существующими ссылками — true,
    с отсутствующим шаблоном — false; развёрнутое — true.
13. Все прежние тесты (`course_store`, `course`, `course_editor`, `active_day_state`,
    `course_scheduler`, `emergency`) без изменений ожиданий, кроме новых групп.

## 7. Риски этапа A

- Два пути чтения дня (own events / ссылка) — закрыт тестами 1–3, 7.
- Кэш как глобальное состояние: mutation только в `prepareTemplates`; при ошибке — пусто.
  В этапе E загрузку кэша нужно выполнить в тех же точках, где меняется поколение
  (boot, Apply, Activate), до публикации дня.
- Пик разбора шаблона с 32 событиями ≈ 84 КБ — на устройстве допустим (такой же пик уже
  даёт разбор дня при Validate), но загрузку кэша следует делать до инициализации WiFi,
  если порядок в `main.cpp` это позволяет (проверить в этапе E).
- Даунгрейд прошивки на шаблонном поколении невозможен (день-ссылка без кэша) — осознанно,
  появится вместе с этапом B.

## 8. Этап A — что сделано (2026-11-23)

Реализовано только хранилище; импорт, публикация, экспорт и планировщик не менялись.

Новое в `course_store`:
- `CourseMeta::layout` (`kLayoutExpanded` по умолчанию, `kLayoutTemplates` при
  `"layout":"tpl1"` в `meta.json`). Неизвестный маркер отклоняется, а не игнорируется.
- `writeTemplates()` — атомарная запись `templates.json` (tmp → bak → rename, CRC-обёртка).
- `prepareTemplates()` / `templatesReady()` / `invalidateTemplates()` и аксессоры
  `cachedTemplateCount/Events/Generation`. Кэш процессный, строго помечен поколением;
  любой сбой (нет файла, CRC, битый JSON, превышение лимитов) очищает его.
- `loadDay()` разрешает `{"template":"name"}` из кэша этого же поколения; при
  отсутствии кэша/шаблона возвращает ошибку — непустой «здоровый» день не подставляется.
- `validateGeneration()` загружает набор шаблонов, если поколение шаблонное.
- `recover()` восстанавливает `templates.json` по тем же правилам, что дни (`.bak`, затем
  `.tmp`), и сбрасывает кэш.
- `deleteGeneration()` удаляет файл шаблонов и кэш этого поколения.
- `cloneGeneration()` для шаблонного поколения копирует `templates.json` и переписывает
  дни с новым generation, сохраняя ссылки (не материализует).

Новое в `course_model` (аддитивно): `toJsonTemplates()` и `fromJsonUnresolved()`.
`fromJson()`/`validate()` не изменили поведение — строгие проверки остались прежними.

Измерения (host, метрика пика и резидента):
- 4 шаблона × 12 событий (файл 5,8 КБ): пик `prepareTemplates` **39 КБ**, резидентно **4,8 КБ**.
- 4 шаблона × 32 события (файл 15,3 КБ): пик **101 КБ**, резидентно **12,1 КБ**.
- Чтение ссылочного дня: файл ≈ 130 Б, разбор ≈ 1–2 КБ (вместо 29–38 КБ для развёрнутого дня).

Результаты: `course_store` 220/220 (было 130), `course` 578, `course_editor` 495,
`course_scheduler` 130, `active_day_state` 275, `emergency` 58; ASan/UBSan по всем
наборам — без ошибок; PlatformIO SUCCESS, RAM 21.0 %, Flash 86.8 % (1 364 757 Б).
