# План хранения курса через шаблоны (JSON v1: templates + days)

Статус: **этапы A–F реализованы и опубликованы** (`6d972f6`); впереди — аппаратные испытания.
Дата: 2026-11-23. Ветка: `standalone-max`. База: `dcb2603`.

## 1. Зачем

Операторский JSON v2 с полным перечислением событий каждого дня даёт большой файл и
заставляет хранилище разворачивать каждый день в отдельный файл: одинаковые расписания
копируются по числу календарных дней. На ESP32 без PSRAM это лишний объём LittleFS,
лишняя RAM на разбор и лишний износ флеша.

Измерено на host тем же кодом хранения:

| Вариант | файлов | LittleFS | макс. файл дня | RAM `loadDay` |
|---|---|---|---|---|
| `docs/course-example.json` (13 дн., 5 шаблонов, 50 уник. событий) | 14 | 21 466 Б | 1 876 Б | 38 КБ (15 событий) |
| операторский профиль 14 дн. (4 шаблона, 42 уник. события, 1 правленый день) | 15 | 14 505 Б | 1 149 Б | 29 КБ (12 событий) |
| тот же курс, уже развёрнутый | 15 | 14 510 Б | 1 149 Б | 29 КБ |
| предлагаемое компактное хранение того же 14-дневного | 16 | ≈6 078 Б | ≈900 Б | цель 1–2 КБ |

Ключевой вывод: материализация сегодня происходит **безусловно**
(`course_store.cpp:678` `toJsonV2(one, true)` внутри `saveDayAtomic`), поэтому шаблонный
и развёрнутый курс на флеше занимают одинаково.

## 2. Архитектура хранения (принята)

```
/course/g<N>/meta.json        — как сейчас; у шаблонных поколений добавляется "layout":"tpl1"
/course/g<N>/templates.json   — НОВЫЙ файл: {"format":"gong-course-templates","version":1,
                                 "templates":{"имя":[event...], ...}}   (та же CRC-обёртка)
/course/g<N>/dNN.json         — формат дня НЕ меняется:
                                 {"days":[{"template":"practice"}]}   ← ссылка
                                 {"days":[{"events":[...]}]}           ← собственные события дня
```

Инварианты:

- Старые опубликованные поколения (`layout` отсутствует = expanded) **не зависят** от
  `templates.json` и читаются ровно как раньше.
- Маркер `layout` пишется только новыми поколениями (этап B). Этап A только умеет его
  читать/писать через `CourseMeta`.
- Смешанное поколение допустимо: часть дней — ссылки, часть — с собственными событиями
  (правка дня материализует только этот день).
- Планировщик по-прежнему загружает только текущий день (`schedule.cpp:185`).

## 3. Этап A — объём работ (Course Store)

Только `server/src/course_store.{h,cpp}` и тесты. Импорт, публикация (Apply) и экспорт
**не меняются**; новых шаблонных поколений на устройстве этот этап не создаёт.

1. `templates.json`:
   - `writeTemplates(generation, map, error)` — атомарная запись (tmp → bak → rename,
     CRC, read-back), как для дней;
   - чтение с проверкой CRC и разбором **по одному шаблону** (пик — один шаблон,
     не весь файл).
2. `TemplateCache` (singleton, строго привязан к generation):
   - `prepareTemplates(generation, error)` — загружает один раз; при смене поколения
     старая запись инвалидируется **до** загрузки новой;
   - `templatesReady(generation)`, `invalidateTemplates()`, счётчики для диагностики;
   - любая ошибка загрузки оставляет кэш пустым (fail-closed).
3. `loadDay()`:
   - день с собственными событиями — как раньше;
   - день-ссылка — разрешается из кэша; нет кэша для этого generation или нет шаблона →
     **ошибка**, а не пустое/частичное расписание.
4. `validateGeneration()` — для `layout=tpl1` сначала готовит кэш, затем проверяет все дни.
5. `recover()` — восстанавливает `templates.json` тем же `recoverBase`, только для
   `layout=tpl1`.
6. `deleteGeneration()` — удаляет `templates.json` (+ `.tmp`/`.bak`) и инвалидирует кэш,
   если удаляется закэшированное поколение.
7. `cloneGeneration()` — копирует `templates.json`, если исходное поколение шаблонное.

Лимиты (проверяются при загрузке, ошибка — понятная строка):
`≤32` шаблона, `≤32` события в шаблоне (правило модели), `≤256` событий суммарно.
Пик RAM при загрузке ≈ один шаблон (12 событий ≈ 30 КБ, 32 события ≈ 84 КБ), резидентно ≈2 КБ.

## 4. Состояния после Apply/Activate (уточнение)

После Apply (в т.ч. первого) корректное состояние: `APPLIED`, `running=false`,
`activation_date=0`, `day_index=-1` (день не привязан, звонков нет). Прежнее ожидание
`day_index=0` в черновике плана было ошибочным — тесты этапов B–F должны проверять `-1`.
После ручной активации дня N: `RUNNING`, `day_index=N`, `activation_date=YYYYMMDD`.

## 5. Что НЕ входит в этап A

- Запись ссылочных дней при импорте/пресетах (этап B).
- Материализация дня при обычной правке (copy-on-write, этап C).
- Компактный экспорт (этап D).
- Загрузка кэша в загрузчике планировщика и при Apply/Activate (этап E).
- Миграция уже опубликованных курсов (не требуется; повторный импорт + Apply).

## 6. Регрессионные тесты этапа A

1. Старое развёрнутое поколение: мета без `layout`, `loadDay` работает без `templates.json`.
2. Шаблонное поколение: `writeTemplates` + мета `tpl1` + дни-ссылки → `loadDay` отдаёт
   ровно события шаблона.
3. Смешанное поколение: день-ссылка и день с собственными событиями в одном поколении,
   каждый даёт свои события.
4. Отсутствующий шаблон у дня-ссылки → ошибка `loadDay`, пустых расписаний нет.
5. Битый `templates.json` (мусор вместо JSON) → `prepareTemplates` = false, кэш пуст,
   `loadDay` ссылочного дня = false.
6. Ошибка CRC (валидный JSON, неверный заголовок) → то же.
7. Неверный generation кэша: после `prepare(A)` чтение ссылочного дня поколения B — ошибка;
   после `prepare(B)` — данные B, без «протечки» A.
8. Сбой загрузки инвалидирует кэш: успешный `prepare`, затем битый файл + `invalidate`/
   повторный `prepare` → кэш пуст, старые шаблоны не отдаются.
9. `recover()` восстанавливает `templates.json` из `.bak` и из `.tmp` после обрыва.
10. `deleteGeneration()` удаляет файл шаблонов и инвалидирует кэш.
11. Лимиты: 33 шаблона → ошибка; >256 событий суммарно → ошибка.
12. `validateGeneration()`: шаблонное поколение с существующими ссылками — true,
    с отсутствующим шаблоном — false; развёрнутое — true.
13. Все прежние тесты (`course_store`, `course`, `course_editor`, `active_day_state`,
    `course_scheduler`, `emergency`) без изменений ожиданий, кроме новых групп.

## 7. Риски этапа A

- Два пути чтения дня (own events / ссылка) — закрыт тестами 1–3, 7.
- Кэш как глобальное состояние: mutation только в `prepareTemplates`; при ошибке — пусто.
  В этапе E загрузку кэша нужно выполнить в тех же точках, где меняется поколение
  (boot, Apply, Activate), до публикации дня.
- Пик разбора шаблона с 32 событиями ≈ 84 КБ — на устройстве допустим (такой же пик уже
  даёт разбор дня при Validate), но загрузку кэша следует делать до инициализации WiFi,
  если порядок в `main.cpp` это позволяет (проверить в этапе E).
- Даунгрейд прошивки на шаблонном поколении невозможен (день-ссылка без кэша) — осознанно,
  появится вместе с этапом B.

## 8. Этап A — что сделано (2026-11-23)

Реализовано только хранилище; импорт, публикация, экспорт и планировщик не менялись.

Новое в `course_store`:
- `CourseMeta::layout` (`kLayoutExpanded` по умолчанию, `kLayoutTemplates` при
  `"layout":"tpl1"` в `meta.json`). Неизвестный маркер отклоняется, а не игнорируется.
- `writeTemplates()` — атомарная запись `templates.json` (tmp → bak → rename, CRC-обёртка).
- `prepareTemplates()` / `templatesReady()` / `invalidateTemplates()` и аксессоры
  `cachedTemplateCount/Events/Generation`. Кэш процессный, строго помечен поколением;
  любой сбой (нет файла, CRC, битый JSON, превышение лимитов) очищает его.
- `loadDay()` разрешает `{"template":"name"}` из кэша этого же поколения; при
  отсутствии кэша/шаблона возвращает ошибку — непустой «здоровый» день не подставляется.
- `validateGeneration()` загружает набор шаблонов, если поколение шаблонное.
- `recover()` восстанавливает `templates.json` по тем же правилам, что дни (`.bak`, затем
  `.tmp`), и сбрасывает кэш.
- `deleteGeneration()` удаляет файл шаблонов и кэш этого поколения.
- `cloneGeneration()` для шаблонного поколения копирует `templates.json` и переписывает
  дни с новым generation, сохраняя ссылки (не материализует).

Новое в `course_model` (аддитивно): `toJsonTemplates()` и `fromJsonUnresolved()`.
`fromJson()`/`validate()` не изменили поведение — строгие проверки остались прежними.

Измерения (host, метрика пика и резидента):
- 4 шаблона × 12 событий (файл 5,8 КБ): пик `prepareTemplates` **39 КБ**, резидентно **4,8 КБ**.
- 4 шаблона × 32 события (файл 15,3 КБ): пик **101 КБ**, резидентно **12,1 КБ**.
- Чтение ссылочного дня: файл ≈ 130 Б, разбор ≈ 1–2 КБ (вместо 29–38 КБ для развёрнутого дня).

Результаты: `course_store` 220/220 (было 130), `course` 578, `course_editor` 495,
`course_scheduler` 130, `active_day_state` 275, `emergency` 58; ASan/UBSan по всем
наборам — без ошибок; PlatformIO SUCCESS, RAM 21.0 %, Flash 86.8 % (1 364 757 Б).

Следующие этапы (B–F) не начаты. При этапе E: вызывать `prepareTemplates()` в точках
смены поколения (boot, Apply, Activate) до публикации дня и проверять largest free block
перед загрузкой набора с 32-событийными шаблонами.

## 9. Этап B — комpactная запись (2026-11-23)

Реализована запись поколений, где уникальные шаблоны хранятся один раз, а дни — ссылки.
**В штатный путь не включена**: HTTP-импорт, Apply и планировщик по-прежнему пишут и
исполняют только развёрнутые поколения. Причина: до этапа E кэш шаблонов не загружается
при boot/Apply/Activate, поэтому шаблонное поколение на устройстве ещё небезопасно.

Новое в `course_store`:
- `writeCompactGeneration()` — создаёт поколение целиком (templates.json → дни → meta
  последней → validateGeneration); при любом сбое поколение удаляется.
- `applyCompactCourse()` / `saveCompactDraft()` — публикация/черновик с теми же
  состояниями, что у `applyCourse()`/`saveDraftCourse()` (APPLIED, `activation_date=0`,
  без running, без автоактивации), плюс откат при ошибке NVS.
- `putDayReference()` / `finishCompactGeneration()` — потоковые строительные блоки для
  импорта: ссылка на шаблон и финальная запись meta+валидация.
- В `templates.json` попадают только фактически используемые шаблоны; лимиты считаются по
  уникальным событиям (≤32 шаблона, ≤32 события в шаблоне, ≤256 суммарно), а не по
  календарным вхождениям.

Новое в `course_editor` (не подключено к маршрутам):
- `importCourseCompact()` — потоковый импорт шаблонного JSON в компактное поколение
  (templates.json один раз, дни-ссылки, дни с собственными событиями — развёрнутые).
  Возвращает ошибку `course has no template references` для курса без шаблонов.

Измерения (host, операторский 14-дневный курс: 4 шаблона × 10 событий, 140 вхождений,
документ 3 990 Б):
- развёрнутая запись: **15 130 Б**, 15 файлов;
- компактная запись: **5 779 Б**, 16 файлов (добавляется `templates.json`) — **0,38×**;
- пик памяти при импорте: 42 КБ в обоих случаях (пик даёт разбор одного шаблона/дня),
  резидентных данных после импорта нет.
В store-тесте тот же профиль с одним индивидуальным днём: 12 157 Б → 5 213 Б (0,43×).

Результаты: `course_store` 368/368, `course` 578, `course_editor` 546, `course_scheduler`
130, `active_day_state` 275, `emergency` 58; ASan/UBSan без ошибок; PlatformIO SUCCESS,
RAM 21.0 %, Flash 86.8 % (1 364 957 Б).

Что нельзя включать на устройстве до этапа E:
- создание шаблонных поколений из штатного импорта/Apply (дни-ссылки не разрешатся,
  планировщик уйдёт в suspend);
- вызов `CourseStore::prepareTemplates()` в boot/Apply/Activate без проверки largest
  free block (пик разбора 32-событийного шаблона ≈ 84–101 КБ);
- экспорт компактного JSON (этап D) и copy-on-write правок (этап C).

## 10. Этап C — copy-on-write для дней с шаблонами (2026-11-23)

Цель: правка одного календарного дня не меняет остальные дни, использующие тот же шаблон.

Как это устроено (без новой логики хранения):
1. `loadDay()` уже разрешает ссылку в отдельный `Day` (этап A) — это и есть «копия».
2. Все редактирующие пути меняют только эту копию в RAM и пишут её через
   `saveDayAtomic()` как **собственный** список `events` (поле `templateName` очищается).
3. `templates.json` и остальные дни не переписываются вообще: их файлы остаются
   байт-в-байт прежними (проверено сравнением).

Что добавлено в этапе C:
- `schedule.cpp`: `courseEnsureTemplates()` — набор шаблонов активного поколения
  подгружается **только** в точках редактирования (`courseDayAddEvent`, `courseDayEditEvent`,
  `courseDayDeleteEvent`, `courseDayJson`). Boot, Apply, Activate, полуночный переход и
  аварийное восстановление не тронуты (этап E).
- `course_editor.cpp`: `editingGeneration()` и `ensureEditableGeneration()` загружают набор
  шаблонов редактируемого поколения. Клон черновика (`ensureDraft` → `cloneGeneration`)
  сохраняет ссылки и копирует `templates.json`, поэтому после клонирования набор уже
  принадлежит новому поколению.
- Активный день по-прежнему правится в RAM (`sched_add/edit/del`) и сбрасывается на диск
  через `courseSaveActiveEntries()` — повторная активация не нужна.

Измерения (host, курс 14 дней × 12 событий в шаблоне):
- COW на уровне store (load + add + save): пик одновременно живых данных **15 КБ**;
- `course_editor::saveDay` на опубликованном компактном курсе (клон черновика + правка
  дня): пик **41 КБ** (клон копирует файлы на flash, а не в RAM);
- резидентных данных после правки нет; `templates.json` не меняется.

Тесты этапа C:
- store: правка ссылочного дня → индивидуальный файл; шаблон и соседние дни не изменены;
  перезагрузка сохраняет индивидуальность; add/edit/disable/remove; несколько
  индивидуальных дней; отказ LittleFS не меняет день; восстановление из `.tmp`;
  кэш другого поколения после клона; развёрнутое поколение не изменилось.
- editor: `dayJson` ссылочного дня с холодным кэшем; `saveDay` пишет в приватный черновик,
  активное поколение не меняется; `clearDay` даёт пустой индивидуальный день.
- scheduler: смешанное tpl1-поколение (день 0 — свои события, дни 1–3 — ссылки), активация
  дня 0, затем `sched_addToDay`/`editInDay`/`delFromDay` по ссылочным дням; после
  «перезагрузки» правки на месте, соседи используют шаблон, активный день не требует
  повторной активации.
- Мутации: убрать загрузку набора в `courseEnsureTemplates()` → 6 падений; убрать её в
  `editingGeneration()` → падает чтение ссылочного дня с холодным кэшем.

Ограничения, которые сохраняются до этапа E:
- Шаблонное поколение нельзя включить в штатный путь: boot/Apply/Activate ещё не
  подгружают набор шаблонов, поэтому после перезагрузки такое поколение уйдёт в suspend.
- Компактный импорт по-прежнему не подключён к HTTP; экспорт (этап D) не изменён.
- В проекте нет `CourseStore::saveDay/clearDay`: соответствующие операции — это
  `CourseStore::saveDayAtomic()` и `course_editor::saveDay()/clearDay()`; поддержаны все
  существующие пути правки.

## 11. Этап D — компактный экспорт (2026-11-23)

Поколения `layout=tpl1` экспортируются как JSON v1: `templates` один раз, дни — ссылки
(`"t3"`) либо собственные массивы событий. Поколения `layout=expanded` экспортируются как
раньше (v2 с полными днями) — поведение не изменилось.

Реализация:
- `CourseStore::loadDayDescriptor()` — читает день **без** разрешения ссылки, поэтому экспорт
  различает «ссылка» и «свой список» и не трогает TemplateCache.
- `CourseStore::openTemplateExport()` / `nextTemplateExportChunk()` — потоковая выдача
  `templates.json` по одному шаблону за чанк; парсинг тот же, что у загрузчика кэша, но
  кэш не заполняется и не инвалидируется.
- `CourseStore::templateExportNames()` — список имён для проверки ссылок: день, ссылающийся
  на отсутствующий шаблон, обрывает экспорт с ошибкой вместо выдачи битого файла.
- `course_editor`: `ExportState` получил `compact`/`phase`/`day`; `beginExport()` определяет
  layout по meta и резолвит поколение **без** подготовки кэша (`exportGeneration()`), чтобы
  экспорт не менял ни кэш, ни календарь, ни LittleFS.

HTTP и GUI не менялись: маршрут по-прежнему тянет `sched_courseExportNext()` в цикле и
склеивает чанки; на устройстве это те же несколько String-ов по размеру чанка.

Размеры и память (host):
- 14-дневный курс (3 шаблона × 4 события + 1 индивидуальный день, 140 вхождений):
  компактный экспорт **1 546 Б** (пик 6 КБ, макс. чанк 431 Б) против развёрнутого
  **5 884 Б** (пик 19 КБ) — 3,8×.
- Худший документируемый случай (47 дней, 8 шаблонов × 32 события = 256 уникальных
  событий): документ **25 155 Б**, 58 чанков, макс. чанк **3 106 Б**, пик **73 КБ** при
  бюджете 96 КБ.

Тесты этапа D (в `course_editor`): форма компактного экспорта (v1, templates, ссылки,
индивидуальный день, `en:false`, кириллица), отсутствие развёртывания шаблонов, экспорт
после COW-правки (active против draft), round-trip export → compact import → apply → export,
сбой/повреждение `templates.json`, ссылка на отсутствующий шаблон, неизменность
развёрнутого экспорта, длины 1/10/20/47, бюджет памяти и размер чанков, а также проверка,
что экспорт не меняет кэш, календарь и файлы.

## 12. Этап E — безопасная интеграция шаблонных курсов (2026-11-23)

Компактные курсы стали штатным форматом: HTTP-импорт сам выбирает хранение по содержимому
документа, boot/Apply/Activate/полночь/восстановление разрешают шаблоны именно
опубликованного поколения.

### Архитектура кэша

- Два слота, каждый строго помечен поколением: **active** (поколение, которое исполняет
  планировщик) и **draft** (всё остальное: проверка, просмотр, правка черновика).
- `prepareActiveTemplates()` вызывают только boot/Apply/Activate/восстановление (и
  `courseLoadDay`, через который они все проходят) — active-слот никогда не вытесняется
  работой с черновиком.
- `prepareTemplates()` (просмотр/правка/валидация) грузит в draft-слот.
- Поиск набора идёт только по совпадению поколения; ошибка загрузки оставляет слот пустым,
  поэтому `loadDay()` падает, а планировщик уходит в SUSPENDED вместо исполнения чужих
  событий.
- Вариант «читать шаблон из LittleFS по требованию» отклонён по измерениям: разбор одного
  шаблона теперь ~5 КБ, резидентный набор ~2 КБ (типично), поэтому кэш дешевле повторных
  чтений на каждом полуночном переходе.

### Память (host, измерено)

| Операция | До этапа E | После |
|---|---|---|
| Validate 47 дней / 256 уник. событий (27 КБ документ) | 77–101 КБ | **8–10 КБ** |
| Разбор одного дня/шаблона на 32 события | 82 КБ | **5 КБ** |
| Import того же курса (включая 35 КБ файлов host-мока) | 197 КБ | **94 КБ** (на устройстве ≈60 КБ) |
| Экспорт худшего случая | 73 КБ | 65 КБ |
| Резидентный набор шаблонов | — | ≈2 КБ (42 события), ≈12 КБ (256) |

Что дало выигрыш:
- `course::parseEventArrayBounded()` — разбор массива событий по одному элементу (пик 5 КБ
  вместо 82 КБ), с теми же правилами и тем же назначением id, что у дерева.
- Валидация шаблонов и дней переведена на этот разбор (день/шаблон больше не строится
  деревом целиком).
- `readFileWithCrc()` — одно выделение: заголовок CRC разбирается на месте и стирается из
  того же буфера (раньше файл копировался дважды).
- `writeFileWithCrc()` / `writeTemplatesParts()` — запись и проверка потоково, CRC считается
  инкрементально; `templates.json` при импорте собирается из диапазонов входного буфера,
  без строки-документа и без векторов событий.
- Импорт больше не строит карту «имя → события»: шаблоны валидируются по одному и пишутся
  потоково.

### Интеграция

- `course_editor::importCourseAuto()` — штатный импорт: если документ ссылается на шаблоны,
  пишется компактное поколение, иначе прежнее развёрнутое (совместимость v2).
- `sched_courseImport()` использует его; Validate/Apply/Activate не менялись по контракту.
- После Apply — APPLIED, `running=false`, `activation_date=0`, `day_index=-1`.
- Activate проверяет набор шаблонов поколения до привязки дня; при ошибке — SUSPENDED.
- Boot: RUNNING-курс публикует день только после успешной загрузки active-набора, иначе
  SUSPENDED (без звонков и без скрытого legacy-запуска).

### Тесты этапа E

Планировщик: APPLIED без звонков, Activate дня 7, звонок по шаблону, reboot с восстановлением
дня 7, полночь → день 8, цикл 13→00, просмотр черновика во время RUNNING (активный слот не
вытесняется, звонки продолжаются), правка другого дня и активного дня без повторной
активации, повторная публикация курса другой длины, отсутствие `templates.json` → SUSPENDED,
битый CRC → SUSPENDED. Редактор: авто-выбор layout, валидация максимального курса в бюджете
64 КБ (пик 10 КБ).

## 13. Этап F — аудит (2026-11-23)

Инструкция для стенда: `docs/DYNAMIC_COURSE_HARDWARE_TEST.md`.

Найдено и исправлено два дефекта:

1. **Импорт вытеснял кэш работающего курса.** `writeTemplates()`/`writeTemplatesParts()`
   вызывали полную инвалидацию кэша (оба слота), поэтому импорт нового черновика во время
   RUNNING сбрасывал набор активного поколения. Следующий полуночный тик обязан был
   перезагрузить его; при фрагментированной куче неудачная перезагрузка отправила бы
   здоровый курс в SUSPENDED. Теперь инвалидируется только набор записываемого поколения.
   Регрессии: `audit_active_templates_survive_draft_write` (store) и
   `audit_import_during_running` (scheduler); мутация «инвалидировать всё» валит тест.

2. **Guard импорта отклонял корректные файлы.** Проверка памяти всё ещё исходила из
   ~78 КБ на день (дерево JSON) и требовала `2×body + 80 КБ`. После этапа E рабочий набор
   — 8–10 КБ, поэтому 27-КБ курс на устройстве со 125 КБ свободных отклонялся. Порог
   пересчитан на `2×body + 24 КБ` (реальные пики: validate 8–10 КБ, import ≈2×body + 8 КБ).

Проверено без изменений: HTTP-путь не копирует документ в `std::string`; Apply не
запускает события (`day_index=-1`, день не публикуется); просмотр/правка черновика идёт
через draft-слот; смешанные дни работают; календарный цикл не тронут; публикация атомарна
(templates → дни → meta → NVS); `recover()` сбрасывает кэш до валидации.

Остаточный риск (не закрыт host-тестами): кэш — общая RAM для loopTask (веб) и controlTask
(планировщик). Разделение на два слота убирает вытеснение, но одновременная первая загрузка
одного и того же поколения из двух задач теоретически возможна (например, Activate из
браузера во время полуночного тика). Проверяется на стенде по `docs/DYNAMIC_COURSE_HARDWARE_TEST.md`.

## 14. Заключительный аудит конкурентного доступа (2026-11-23)

### Контексты выполнения

| Контекст | Что делает с кэшем | Под sys_lock? |
|---|---|---|
| `controlTask` (`main.cpp:42-58`) | `sys_lock(); sched_check(); sys_unlock();` → `courseAdvance` → `coursePublishDay` → `courseLoadDay` → `prepareActiveTemplates` + `lookupTemplate` | **да** |
| loopTask, обычные маршруты (`dispatch()`, `webhandler.cpp:388-391`) | читают состояние, `/api/course/activate` (R_WRITE) → `prepareActiveTemplates` | **да** |
| loopTask, `R_NOLOCK`-маршруты (`webhandler.cpp:1108-1124`): import, apply, insert, clear, preset, rename, discard, draft PUT/DELETE | `importCourseAuto` → `writeTemplatesParts`/`invalidateTemplatesFor`; `validateGeneration` → `prepareTemplates`; `applyDraft` → `prepareTemplates`; `sched_courseApply` → `prepareActiveTemplates` | **нет** |
| loopTask, `/api/course/export` (R_STREAM) | только `loadDayDescriptor`/`openTemplateExport`, кэш не трогает | нет (и не нужно) |
| audioTask (`mp3handler`) | кэш не использует | — |

Вывод: доступ **не был сериализован**. controlTask держит `sys_lock`, но обработчики импорта/публикации/правки черновика работают вне него, поэтому на одном ядре (вытеснение по тикам) возможны: чтение карты одним task в момент `clear()`/`swap()` другим, двойная загрузка одного поколения, чтение частично обновлённого набора.

### Реализованная синхронизация

- `CacheGuard` — **листовой** мьютекс внутри `course_store` (на устройстве
  `xSemaphoreCreateMutexStatic`, на host — атомарный флаг, чтобы регрессия шла по тому же коду).
- Загрузка набора (**LittleFS + разбор**) выполняется **вне** блокировки, в локальном объекте;
  под блокировкой — только короткая замена: `slot.items.swap(loaded.items)` и три поля, затем
  старые данные освобождаются уже вне блокировки. Аудиопоток не блокируется.
- Перед заменой состояние **перепроверяется** под блокировкой: если другое task уже
  загрузило это поколение, чужой полный набор сохраняется.
- Чтение никогда не отдаёт указатель в карту: `lookupTemplate()` копирует события одного
  шаблона (≤32 события) под блокировкой.
- Инвалидация (`invalidateTemplates`, `invalidateTemplatesFor`) и аксессоры — под блокировкой.
- Порядок блокировок один: `sys_lock → cacheMutex`. `course_store` никогда не берёт
  `sys_lock`, поэтому цикл (deadlock) невозможен; рекурсии нет — ни одна функция под
  `CacheGuard` не вызывает другую блокирующую функцию кэша.

### Тесты

- `cache_commit_rechecks_after_concurrent_load` — hook между сборкой и коммитом эмулирует
  «другое task уже загрузило это поколение»; набор остаётся полным и корректным.
- `cache_invalidate_during_commit_is_atomic` — hook очищает кэш во время сборки; после
  коммита набор либо целиком есть, либо отсутствует (частичного состояния нет).
- `cache_lookup_returns_a_copy` — вызывающий не может испортить кэш; чужое поколение не
  обслуживается.

Host-тесты однопоточные, поэтому взаимное исключение как таковое проверяется на стенде;
здесь проверена атомарность протокола «сборка вне блокировки → перепроверка → замена».

### 14.1 Ревизия поколений (закрытие «устаревшей публикации»)

Найден ещё один дефект протокола: `prepareTemplates()` собирал набор вне блокировки и при
коммите проверял только «есть ли уже набор этого поколения». Если между сборкой и коммитом
другое task перезаписывало `templates.json` этого же поколения (или удаляло его), коммит
публиковал **прочитанное до записи** содержимое — то есть устаревшие события.

Механизм:
- `g_generationStamp[generation]` — счётчик мутаций конкретного поколения, увеличивается в
  `invalidateTemplatesFor()` (вызывается после `writeTemplates`/`writeTemplatesParts` и из
  `deleteGeneration`);
- `g_globalEpoch` — увеличивается при полной очистке (`invalidateTemplates`, в том числе
  `recover()`);
- `prepareTemplates()`/`prepareActiveTemplates()` фиксируют обе ревизии **до** сборки и
  перепроверяют их под блокировкой перед заменой. Если ревизия изменилась, набор
  отбрасывается с ошибкой `template generation N changed while loading` и в кэш не попадает;
  следующий вызов читает уже новый файл.

Мутация чужого поколения загрузку не прерывает (проверяется отдельным тестом), поэтому
импорт черновика не может «сорвать» полуночную загрузку активного курса.

Тесты: `cache_stale_load_is_not_republished` (перезапись поколения во время сборки → отказ,
затем новый набор с новыми событиями), `cache_unrelated_write_does_not_abort`,
`cache_invalidate_during_commit_is_atomic` (обновлён под новый контракт). Отключение проверки
ревизии мутацией валит три проверки.
